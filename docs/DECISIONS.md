## 1. เปลือกแอป: Tauri 2 + React

ตามข้อเสนอ D01–D02 และตรงกับ PuriCat (`~/Dev/Rust/PuriCat`) ที่เจ้าของผลิตภัณฑ์ชี้ให้ใช้เป็นแนวทาง
เวอร์ชัน frontend ใช้ชุดเดียวกับ PuriCat ซึ่ง build ผ่านบนเครื่องนี้แล้ว เวอร์ชันจริงถูกตรึงด้วย `Cargo.lock` และ `pnpm-lock.yaml`

Tauri วาด UI ด้วย WebView ของระบบ (WKWebView) จึงเป็น "แอป desktop ที่มี Rust backend" ไม่ใช่ native controls

## 2. `crates/core` แยกจาก Tauri — ต่างจากเอกสาร

Blueprint หมวด 15 วางโมดูลไว้ใต้ `src-tauri/src/{commands,domain,services,storage,…}` งานนี้ย้ายตรรกะทั้งหมดไปที่ crate `puri-core`
แล้วให้ `src-tauri` เหลือไฟล์เดียว

- เหตุผล: ทดสอบกติกาข้อมูลได้ด้วย `cargo test` โดยไม่ต้องมีหน้าต่าง, compile เร็ว, ใช้ core ร่วมกับ dev bridge และเครื่องมือ CLI ในอนาคตได้
  (เหตุผลเดียวกับ ADR 0002 ของ PuriCat)
- ขอบเขตความรับผิดชอบของหมวด 7.2 ยังอยู่ครบในรูปโมดูลของ core: `db` `import` `jobs` `media` `catalog` `people` `faces` `export`
  `legacy` `platform` `assets` `api`
- ผลที่ตามมา: โค้ดใน core ห้าม `use tauri`

## 3. IPC: คำสั่งโดเมนที่มีชนิด ผ่าน dispatcher เดียว

`src-tauri` ลงทะเบียนคำสั่ง Tauri ตามรายชื่อใน `api::COMMAND_NAMES` (45 คำสั่ง) ด้วย macro `domain_commands!` แต่ละตัวส่ง
`(ชื่อ, args)` ไป `puri_core::api::dispatch` ซึ่ง deserialize เป็น enum `Command` — argument ผิดชนิดหรือชื่อที่ไม่รู้จักถูกปฏิเสธ

- ไม่มีคำสั่ง SQL, shell หรืออ่านไฟล์ด้วย path อิสระ; UI ส่ง ID เท่านั้น ยกเว้น path ที่ผู้ใช้เลือกเอง (โฟลเดอร์นำเข้า, ปลายทางส่งออก)
- เทสต์ `ipc_contract_matches_typescript_command_table` เทียบรายชื่อใน `src/lib/ipc/types.ts` กับ `COMMAND_NAMES`
  และเทสต์ใน `src-tauri` เทียบ macro กับ `COMMAND_NAMES` — กัน Rust/TypeScript ไม่ตรงกันในระดับชื่อคำสั่ง
- **ยังไม่ทำ:** ตรวจรูปร่างของ DTO ทั้งสองฝั่งอัตโนมัติ (ตอนนี้ตรงกันด้วยการเขียนมือ) และยังไม่ได้จำกัดคำสั่งด้วย `AppManifest`
  ของ Tauri (Blueprint 7.3) — หน้าต่างมีเดียวและโหลดเฉพาะ asset ในแอปภายใต้ CSP

## 4. ฐานข้อมูล

- ไฟล์ `library/library.sqlite` ใน app data; cache (ภาพย่อ, ครอปใบหน้า) อยู่ใน app cache แยกจากฐาน และสร้างใหม่ได้
- `PRAGMA application_id` = `0x50555249` ใช้แยกคลังของเราจาก SQLite อื่น: เปิดไฟล์ที่ไม่ใช่คลังจะถูกปฏิเสธโดยไม่แก้ไฟล์
- migration เรียงตาม `PRAGMA user_version`; คลังที่ใหม่กว่าแอปถูกปฏิเสธ ไม่ downgrade
- `library.lock` (file lock ของระบบ) กันสอง process เปิดคลังเดียวกัน
- ผู้เขียนมีสองตัว: connection ของคำสั่ง UI (หลัง mutex) และ connection ของ worker; ใช้ WAL + `busy_timeout` 15 วินาที
- คลังถูกเก็บเป็นชุดสำรองก่อนทุก migration (`backup::before_upgrade`) ถ้าเก็บไม่ได้แอปไม่อัปเกรดและไม่เปิดคลัง — เปิดด้วยแอปรุ่นเดิมได้ต่อ
- **สำรอง/กู้คืน** ([DATA_MODEL.md](DATA_MODEL.md) หมวดสำรองข้อมูล): กู้คืนแบบ "วางรอแล้วสลับตอนเปิดแอป" แทนการสลับฐานข้อมูลขณะแอปเปิดอยู่
  เพราะมีผู้เขียนสองตัว (UI และ worker) และ cache ในหน่วยความจำหลายชุด การสลับตอนเปิดไม่ต้องหยุดอะไรกลางทางและย้อนได้เสมอ
  ต่างจาก Blueprint 13.4 ที่ให้ "เปิดเป็นคลังใหม่" เป็นค่าเริ่มต้น: แอปยังมีคลังเดียว จึงใช้การเก็บคลังปัจจุบันเป็นชุด `before_restore` แทน
- **ยังไม่ทำ:** checksum ของ migration, เลือกชนิดข้อมูลที่รวมในชุดสำรอง, สำรองไปที่อื่นตามตาราง

## 5. ตัวตนของไฟล์

`photo_locations.path_key` คือ path จาก `std::fs::canonicalize` ไม่ lowercase และไม่ normalize Unicode ทับ (หมวด 7.4)
path เดิมที่พบผ่าน parent หรือ child ใช้ `photo_id` เดิม สำเนาเหมือนกันทุก byte ที่คนละ path เป็นคนละ `photo_id` และมี SHA-256 เดียวกัน

**ยังไม่ทำ:** `volume_key` / filesystem file ID สำหรับตามไฟล์ที่ถูกเปลี่ยนชื่อ และ relink (Phase 3)
ไฟล์ที่หายถูกทำเครื่องหมาย `available = 0` ไม่ลบ

## 6. สิทธิ์ไฟล์บน macOS

รุ่น Python แจกนอก App Store ด้วย Developer ID และไม่ใช้ sandbox รุ่นนี้เสนอแบบเดียวกัน: path ที่ผู้ใช้เลือกผ่าน native picker
ถูกเก็บเป็น path ธรรมดา ไม่ใช้ security-scoped bookmark

ผลที่ตามมา: ถ้าภายหลังต้องเข้า App Store ต้องเพิ่ม bookmark ใน `platform` และทดสอบสิทธิ์หลังเปิดแอปใหม่
macOS อาจถามสิทธิ์เข้าโฟลเดอร์ Desktop/Documents/ไดรฟ์ภายนอกครั้งแรก — **ยังไม่ได้ทดสอบกับ build ที่เซ็นแล้ว**

ตัวติดตั้ง: `scripts/release-mac.sh` สร้างแอป universal เซ็นด้วย Developer ID + hardened runtime (ไม่มี entitlement เพิ่ม)
แล้ว notarize และ staple DMG ผ่านโปรไฟล์ keychain ของ notarytool ไม่มีโมเดลใบหน้าหรือ ONNX Runtime อยู่ในตัวติดตั้ง
ตั้งแต่ `v2.0.0-alpha.2` ตัวติดตั้งที่เผยแพร่สร้างโดย workflow `Release` บน GitHub Actions (push tag `v*` → build + เซ็น + notarize + แนบกับ release;
ใบรับรองและรหัส notarize เป็น secret ของ repo ที่เจ้าของใส่เองด้วย `scripts/setup-release-secrets.sh`) การอัปเดตในแอปอยู่ในข้อ 13

**เชื่อมตำแหน่งโฟลเดอร์ใหม่** (`relink.rs`, S14/T13): ผู้ใช้ชี้โฟลเดอร์ของกิจกรรมที่ตำแหน่งใหม่ แอปจับคู่รูปเดิมด้วย **ตำแหน่งสัมพัทธ์ในโฟลเดอร์ + ขนาดไฟล์**
ไม่ได้ hash เนื้อไฟล์ (รูปส่วนใหญ่ไม่มี SHA-256 เก็บไว้ และการอ่าน 53 GB เพื่อยืนยันช้าเกินไป) หน้ายืนยันจึงบอกหลักฐานที่ใช้ตรง ๆ
ไฟล์ที่ขนาดไม่ตรงหรือไม่อยู่ที่ตำแหน่งเดิมไม่ถูกผูกกับไฟล์อื่น และยังอยู่ในคลังพร้อมชื่อบุคคลเดิม กิจกรรมอื่นของแหล่งรูปเดียวกันที่หาโฟลเดอร์เดิมไม่เจอ
และพบที่ตำแหน่งใหม่แบบเดียวกันถูกเสนอให้ย้ายพร้อมกัน (ย้ายโฟลเดอร์แม่ 219 งานแก้ได้ในครั้งเดียว) โฟลเดอร์ที่เป็นของกิจกรรมอื่นอยู่แล้วถูกปฏิเสธ
ยังไม่ทำ: จับคู่ไฟล์ที่ถูกเปลี่ยนชื่อหรือย้ายข้ามโฟลเดอร์ย่อย, หน้ารวมแหล่งรูป

## 7. การเสิร์ฟรูป

`puri://localhost/{thumb|photo|face}/{id}` และ `draft/{previewId}/{draftId}` — Rust แปลง ID เป็นไฟล์เอง
ไม่เปิด asset scope ของ Tauri และไม่ให้สิทธิ์ `fs` กับ web view ตัวดูภาพโหลด bytes ของต้นฉบับ (ไม่ re-encode)
และ WebView หมุนตาม EXIF เอง จึงใช้ transform เดียวกับพิกัดกรอบใบหน้า (สัดส่วนบนภาพที่หมุนแล้ว)

## 8. ถอดรหัสรูปและภาพย่อ

crate `image` 0.25 เปิดเฉพาะ JPEG และ PNG; UI รายงานชนิดอื่นว่า "ยังไม่รองรับ" พร้อมจำนวน ไม่ทำให้หายเงียบ

JPEG ใช้ crate `jpeg-decoder` ถอดแบบย่อระหว่างถอด (DCT scaling 1/2–1/8) สำหรับภาพย่อ; ไฟล์ที่ทางลัดนี้ไม่รับจะกลับไปใช้ `image`

ผลวัดจริง (debug build ที่ dependency ใช้ `opt-level = 3`, MacBook Apple M4 / 24 GB, macOS 26.7, SSD ในเครื่อง, 5 threads,
รูป JPEG จากกล้อง 8096×5397 จำนวน 292 รูปจากสามโฟลเดอร์งานจริง, รวม hash SHA-256 + EXIF + ภาพย่อ 512px, ไม่มีรูปผิดพลาด):

| วิธี | เวลา | อัตรา |
|---|---|---|
| `image` ถอดเต็มภาพ | 34.9 วินาที | 8.4 รูป/วินาที |
| `jpeg-decoder` ถอดแบบย่อ (ที่ใช้อยู่) | 26.9 วินาที | 10.9 รูป/วินาที |

วัดอย่างละหนึ่งรอบ ไฟล์อยู่ใน cache ของระบบแล้วทั้งสองรอบ คลัง 19,687 รูปของผู้ใช้จะใช้ราว 30 นาทีถ้าอัตราคงที่
(ค่าประมาณก่อนมีการวิเคราะห์ใบหน้า; รอบจริงพร้อมวิเคราะห์ใบหน้าดูข้อ 9) เวลาส่วนใหญ่อยู่ที่การถอด entropy ของ JPEG 44 ล้านพิกเซล ซึ่งการย่อไม่ช่วย

**RAW รองรับแล้ว (21 พ.ย. 2569) ด้วย crate `rawler` ไม่ใช่ ImageIO — ข้อ 25** · HEIC ยังไม่รองรับ (แผนเดิม: adapter ที่เรียก ImageIO ของ macOS
— ยังไม่ได้ทดลอง)

## 9. โมเดลใบหน้า — InsightFace `buffalo_l` ดาวน์โหลดในแอปด้วยปุ่มเดียว

**การตัดสินใจของเจ้าของผลิตภัณฑ์ (18 พ.ย. 2569):**

1. การใช้งานของโครงการไม่ใช่เชิงพาณิชย์ จึงใช้โมเดลของ InsightFace ได้
2. "ใช้ตัวที่ดีที่สุด ที่แม่นที่สุด" → เปลี่ยนจากชุดเล็ก `buffalo_sc` ของรุ่น Python เป็น **`buffalo_l`**
3. "ทำให้มันง่ายที่สุด" สำหรับผู้ใช้ → แอปติดตั้งโมเดลเองด้วยปุ่มเดียว ไม่มีการเลือกไฟล์หรือโฟลเดอร์

เหตุผลที่เลือก `buffalo_l`: ตารางของ InsightFace (`python-package/README.md`) ให้ MR-ALL 91.25 / IJB-C(E4) 97.25 เทียบกับ 71.87 / 95.02
ของ `buffalo_s`/`buffalo_sc`; เป็นชุดมาตรฐานของไลบรารีและดาวน์โหลดอัตโนมัติได้ ชุด `antelopev2` (ResNet100@Glint360K) ไม่มีตัวเลขในตารางเดียวกัน
และต้นทางระบุว่าดาวน์โหลดอัตโนมัติไม่ได้ จึงไม่เลือก

| | `buffalo_l` (ที่ใช้) | `buffalo_sc` (รุ่น Python) |
|---|---|---|
| ตรวจใบหน้า | SCRFD-10GF `det_10g.onnx` (16.9 MB) | SCRFD-500MF |
| จำใบหน้า | ResNet50@WebFace600K `w600k_r50.onnx` (174 MB), 512 มิติ | MobileFaceNet@WebFace600K, 512 มิติ |
| ไฟล์ดาวน์โหลด | `buffalo_l.zip` 288,621,354 bytes จาก release v0.7 ของ InsightFace บน GitHub | 16 MB |

**วิธีติดตั้ง (ทำแล้ว):** ไฟล์โมเดลไม่อยู่ในตัวติดตั้งและไม่อยู่ใน repo ผู้ใช้กดปุ่มเดียว → งานเบื้องหลังดาวน์โหลด zip จากต้นทาง
(ทำต่อจากเดิมได้เมื่อเน็ตหลุด) → แตกเฉพาะสองไฟล์ที่ใช้ → ตรวจ SHA-256 กับค่าที่ฝังในแอป → วิเคราะห์รูปที่มีในคลังต่อเอง
ไฟล์ที่ checksum ไม่ตรงถูกปฏิเสธ UI แสดงที่มาและเงื่อนไข "ใช้ได้เฉพาะงานที่ไม่ใช่เชิงพาณิชย์" ข้างปุ่มดาวน์โหลด

เหตุผลที่ไม่รวมไฟล์ในตัวติดตั้ง: (1) ตัวติดตั้งจะโตจาก 13 MB เป็นราว 300 MB (2) ข้อความสัญญาอนุญาตพูดถึงการใช้ ไม่พบข้อความอนุญาตให้แจกจ่ายต่อ
และตัวติดตั้งของเราเปิดให้ใครก็ดาวน์โหลดได้ การให้แอปดึงจากต้นทางเองเป็นวิธีเดียวกับไลบรารี Python ของ InsightFace
ผลต่อผู้ใช้: ต้องมีอินเทอร์เน็ตหนึ่งครั้งตอนติดตั้งโมเดล รูปของผู้ใช้ไม่ถูกส่งออกจากเครื่อง

**ผลที่ตามมาของการเปลี่ยนโมเดล:**

- เวกเตอร์ 46,375 ตัวของฐานรุ่น Python อยู่คนละ embedding space จึง **ไม่ถูกนำมาใช้** (ตารางเก็บ `space` ทุกเวกเตอร์ และเทียบเฉพาะ space เดียวกัน)
  รายชื่อ กลุ่ม และภาพครอปใบหน้าตัวอย่าง 522 ใบถูกนำเข้าได้ ภาพครอปถูกสร้างเวกเตอร์ใหม่ด้วย `buffalo_l`
- ช้ากว่าชุดเล็ก: ดูผลวัดด้านล่าง
- ตัวดาวน์โหลดใช้ `curl` และ `unzip` ของระบบบน macOS, `curl.exe` และ `tar.exe` ใน System32 บน Windows (ส่ง argument ตรง ๆ ไม่ผ่าน shell — ข้อ 12)

### ONNX Runtime ใน Rust (D07)

crate `crates/faces` ใช้ `ort` 2.0.0-rc.15 (ONNX Runtime 1.31 แบบ static library ที่ดาวน์โหลดตอน build) และ implement
`puri_core::ai::FaceAnalyzer`; core ไม่รู้จัก ONNX Runtime และเทสต์ของ core ใช้ตัววิเคราะห์จำลอง

- **ความเข้ากันได้ของ pipeline:** พิสูจน์กับชุด `buffalo_sc` เทียบฐานรุ่น Python — cosine มัธยฐาน 0.985 จาก 9,084 ใบหน้า
  ([LEGACY_AUDIT.md](LEGACY_AUDIT.md) หมวด 3.3) pipeline เดียวกันนี้ใช้กับ `buffalo_l` โดยเปลี่ยนเฉพาะไฟล์โมเดล
- **Mac Intel ไม่มีตัววิเคราะห์ใบหน้า:** `ort` ไม่มี ONNX Runtime สำเร็จรูปสำหรับ `x86_64-apple-darwin` crate จึงตัด `ort` ออกบนเป้าหมายนั้น
  แอป universal ยัง build ได้ ส่วน Intel รายงาน `faceAnalysis.state = unsupported` พร้อมเหตุผล และใช้การระบุใบหน้าเองได้
  (ตรวจแล้วว่า compile ผ่าน **ยังไม่เคยรันบน Mac Intel**) ทางแก้ภายหลัง: build ONNX Runtime เอง หรือใช้ตัวรันแบบ pure Rust
- **macOS ขั้นต่ำขยับเป็น 13.4** เพราะ static library ของ ONNX Runtime build สำหรับ 13.4 ขึ้นไป
- ต้องลิงก์ runtime ของ clang เอง (`crates/faces/build.rs`); `ort` ยังเป็น release candidate; ONNX Runtime ไม่ใช่ pure Rust
- **CoreML (แก้ 21 พ.ย. 2569):** เดิมเข้าใจว่าใช้ CPU อย่างเดียว แต่ ONNX Runtime 1.31 บน Apple Silicon เปิด CoreML ให้เอง
  และแปลงโมเดลใหม่ทุกครั้งที่โหลด (3–4 วินาที) ไปวางใน `$TMPDIR` ครั้งละราว 365 MB ซึ่งลบเฉพาะเมื่อโปรแกรมปิดแบบปกติ —
  แอปที่ปิดโดยไม่คืน session เทสต์ และ dev build จึงทิ้งไว้ทุกครั้ง (เจอจริง 432 รายการ 9.8 GB จนดิสก์ Mac เต็ม)
  ตอนนี้ตั้ง CoreML เองพร้อมที่เก็บโมเดลที่แปลงแล้วใน `<โฟลเดอร์โมเดล>/coreml-cache/<ไฟล์>-<ขนาด>-<เวลาแก้ไข>/` ใช้ซ้ำทุกครั้ง
  (โหลดเหลือราว 0.2 วินาที · ผลของโมเดลเท่าเดิมทุกบิตเทียบกับที่ ONNX Runtime เปิดเอง · ไม่มีไฟล์ใน `$TMPDIR` แม้ถูก kill กลางคัน)
  และตอนโหลดโมเดลลบ `onnxruntime-*.model.mlmodel(c)` ใน `$TMPDIR` ที่ PID ในชื่อไม่ทำงานแล้ว (ของแอปรุ่นก่อน เทสต์ dev build)
  · ไม่ใช้ CPU อย่างเดียวเพราะเวกเตอร์ใบหน้าของ CPU ต่างจาก CoreML เล็กน้อย (คลังที่วิเคราะห์แล้วคำนวณด้วย CoreML) และ
  เวกเตอร์ช้ากว่า ~4 เท่า · สร้างโฟลเดอร์ที่เก็บไม่ได้ = ใช้ CPU แทน (ไม่ทิ้งไฟล์ใน `$TMPDIR`)

ผลวัดกับรูปจริง (debug build, Apple M4, รูป JPEG 8096×5397 จากสามโฟลเดอร์งาน 292 รูป, วัดหนึ่งรอบ):

| | เวลา | อัตรา |
|---|---|---|
| เตรียมข้อมูลรูปอย่างเดียว (ไม่มีโมเดล) | 26.9 วินาที | 10.9 รูป/วินาที |
| เตรียมข้อมูลรูป + วิเคราะห์ใบหน้าด้วย `buffalo_l` (พบ 1,096 ใบหน้า) | 123.3 วินาที | 2.4 รูป/วินาที |

ตัวเลข debug ช้าเพราะโค้ดของ `crates/faces` (จัดหน้า 112×112, เตรียม tensor) ไม่ถูก optimize ใน debug — ไม่ใช่ตัวโมเดลช้า
วัดแยกขั้นใน release (`crates/faces/examples/bench.rs`): ถอดรหัส+ย่อ ~75 ms, ตรวจใบหน้า ~35 ms, เวกเตอร์ ~3.5 ms/ใบหน้า ต่อรูป
จึงไม่ได้ตั้งใจเปิด CoreML ตอนนั้น: คอขวดคือการถอดรหัส JPEG 43 ล้านพิกเซล ไม่ใช่ inference (ภายหลังพบว่า ONNX Runtime เปิดเองอยู่แล้ว — ดูข้อ CoreML ข้างบน)

คลังจริงทั้งโฟลเดอร์ (19,686 รูป, 76,145 ใบหน้า) ใช้ 42 นาทีสำหรับการวิเคราะห์ครั้งแรก = 7.8 รูป/วินาที ต่ำกว่าที่วัดกับ 292 รูป
(วัดด้วย dev bridge แบบ release รอบเดียว — [TEST_REPORT.md](TEST_REPORT.md) หมวด "คลังใหญ่")
ระหว่างนั้นดูรูป ค้นหา และตั้งชื่อใบหน้าที่วิเคราะห์เสร็จแล้วได้ งานพักและทำต่อได้

**ครอปใบหน้าทำตอนวิเคราะห์** (18 พ.ย. 2569): งานวิเคราะห์ถอดรหัสรูปอีกหนึ่งครั้งต่อรูปที่พบใบหน้า ในขนาดเท่าที่ใบหน้าเล็กสุดต้องการ
(ย่อระหว่างถอดได้ถึง 1/8) แล้วเขียนครอป 256 px ของทุกใบลง cache เหตุผล: รูป 8096 px ที่ตัววิเคราะห์ใช้ถูกย่อเหลือ 1280 px
ครอปจากภาพนั้นได้ไม่ถึง 96 px สำหรับใบหน้ากว่าครึ่ง (592 จาก 1,099) จึงเบลอเกินจะใช้ตรวจ ส่วนการสร้างตอนถูกขอต้องถอดรหัสต้นฉบับ
ทีละใบทำให้คิวตรวจสอบขึ้นช้า ต้นทุนที่วัดได้รวมอยู่ใน 25.1 วินาทีข้างบนแล้ว

**คิวตรวจสอบกับงานวิเคราะห์ที่ยังวิ่ง:** ตัวนับสองตัวใน `meta` — `identity_revision` เพิ่มเมื่อมีใบหน้า/เวกเตอร์ใหม่หรือมีการตัดสิน
(คิวรอบถัดไปคิดใหม่) และ `decision_revision` เพิ่มเฉพาะเมื่อผู้ใช้ตัดสิน (ยืนยัน เพิกถอน ปฏิเสธ ไม่ใช่ใบหน้า เก็บ/คืนบุคคล)
`get_review_faces` เสิร์ฟจากคิวที่ออกไปแล้วและตอบ `PREVIEW_STALE` เฉพาะเมื่อ `decision_revision` เปลี่ยน
รายการที่ผู้ใช้เปิดดูอยู่จึงไม่เก่าเพียงเพราะมีรูปถูกวิเคราะห์เสร็จเพิ่ม

**เกณฑ์ของข้อเสนอ (ยังไม่ได้ปรับเทียบ):** เสนอชื่อเมื่อ cosine ≥ 0.45, ป้าย "ใกล้เคียงมาก" เมื่อ ≥ 0.60, รวมกลุ่มใบหน้าที่ยังไม่ทราบชื่อเมื่อ ≥ 0.50

**ใบหน้าที่ตัวตรวจไม่มั่นใจ** (คะแนนตัวตรวจต่ำกว่า 0.6 — ในคลังทดสอบ 176 จาก 1,099 ใบ ส่วนหนึ่งเป็นท้ายทอยและหน้าเบลอนอกโฟกัส):
เจ้าของผลิตภัณฑ์ตัดสิน 18 พ.ย. 2569 ให้**ไม่เสนอชื่อและไม่จัดกลุ่ม**ใบเหล่านี้ (`MIN_DETECTION_SCORE` ใน `review.rs`) กรอบยังถูกเก็บ
ยังเห็นในตัวดูภาพ ตั้งชื่อเองได้ และนับอยู่ใน "ใบหน้าที่ยังไม่เข้ากลุ่มใด" เหตุผล: ข้อเสนอผิดที่เจอตอนไล่ดูด้วยตามาจากช่วงคะแนนนี้ทั้งหมด
ตัวตรวจยังใช้เกณฑ์ 0.5 เท่ารุ่น Python จึงไม่มีใบหน้าหายไปจากคลัง ถ้าภายหลังเปลี่ยนเกณฑ์ ไม่ต้องวิเคราะห์ใหม่
เป็นค่าตั้งต้นจากรุ่นเดิม ไม่มีชุดข้อมูลที่ติดป้ายแล้วสำหรับวัดความแม่นยำ จึงไม่แสดงเป็นเปอร์เซ็นต์

**AI จัดให้ก่อน ผู้ใช้แจ้งเฉพาะที่ผิด** — เจ้าของผลิตภัณฑ์ตัดสิน 18 พ.ย. 2569 หลังลองคลัง 19,686 รูป (แทนกติกาเดิม "ทุกข้อเสนอต้องยืนยัน"
และ T18 ที่ให้ข้อเสนอไม่ปนในผลค้นหา): หลังวิเคราะห์ หน้าบุคคลขึ้น 0 รูปทุกคนจนกว่าจะกดยืนยันทีละกลุ่ม ซึ่งใช้งานจริงไม่ได้กับใบหน้าหลายหมื่นใบ
- รูปที่ AI จับคู่ได้ (cosine ≥ 0.45) **นับเป็นรูปของบุคคลนั้นเลย** ในการ์ดบุคคล หน้ารายละเอียดบุคคล ดูเร็ว และการค้นหา (ค่าเริ่มต้น `includeSuggested`)
  โดยมีเครื่องหมายบอกว่ายังไม่มีคนตรวจ ปิดได้เพื่อดูเฉพาะรูปที่ยืนยันแล้ว
- ผู้ใช้เลือกรูปที่ไม่ใช่แล้วกด "ไม่ใช่ …" (`reject_suggestions`): คู่ใบหน้า–บุคคลนั้นไม่ถูกจัดให้อีก
- **ผลจับคู่ไม่ใช่คำยืนยัน และไม่ถูกเก็บลงคลัง**: ไม่มีแถวใน `face_assignments` ถูกสร้างแทนผู้ใช้ ตัวอย่างที่ใช้เทียบยังมาจากใบหน้าที่ผู้ใช้ยืนยัน
  และใบหน้าตัวอย่างที่นำเข้าเท่านั้น รูปที่ AI เดาผิดจึงไม่ถูกนำไปใช้เดาต่อ ผลจับคู่อยู่ในตารางชั่วคราว `temp.ai_matches` ของการเชื่อมต่อ
  คำนวณใหม่เมื่อข้อมูลตัวตนเปลี่ยน (`review::ensure_matches`) — ไม่มีการเปลี่ยน schema
- จับคู่ **ครบทุกใบหน้าที่เข้าเกณฑ์** (เดิมคิดเฉพาะ 12,000 ใบแรก) เพดาน 12,000 เหลือเฉพาะการจัดกลุ่มใบหน้าที่ไม่ทราบชื่อ
  และหน้าตรวจสอบบอกจำนวนใบที่ยังไม่ได้จัดกลุ่มแยกจาก "ใบเดี่ยว"
- เวกเตอร์ของใบหน้าที่ยังไม่มีชื่อถูกเก็บในหน่วยความจำข้ามรอบคำนวณ (~2 MB ต่อพันใบ; 68,453 ใบ ≈ 140 MB) เพราะการอ่านจาก SQLite ทุกรอบช้าเกินไป
- ยังนับเฉพาะที่ยืนยันแล้ว: รายการ "ปรากฏร่วมในภาพ", รายชื่อบุคคลในหน้ากิจกรรม, ภาพตัวแทนของบุคคล และคำสั่ง API ที่ไม่ได้ขอ `includeSuggested`

ผลกับคลังทดสอบ 19,686 รูป: จับคู่ได้ 16,452 ใบหน้าใน 92 คน (เดิมเห็น 4,251 ใบ) ตัวเลขเวลาอยู่ใน [TEST_REPORT.md](TEST_REPORT.md) หมวด "AI จัดให้ทั้งคลัง"

## 10. การทดสอบแอปจริง

WKWebView ไม่มี WebDriver จึงใช้วิธีของ PuriCat (ADR 0012): debug build อ่าน `PURI_E2E_SCRIPT` แล้วฉีดสคริปต์เข้าในหน้าต่างจริง
สคริปต์ขับ DOM และรายงานผ่านคำสั่ง `e2e_report`; `PURI_E2E_PICK` เตรียมคำตอบของ native folder picker; `PURI_DATA_DIR`

`PURI_LEGACY_DB` (debug เท่านั้น) ชี้ตำแหน่งฐานของรุ่น Python: เทสต์ตั้งเป็นฐานจำลอง หรือ path ที่ไม่มีไฟล์ เพื่อไม่ให้ฐานจริงบนเครื่องผู้พัฒนา
ทำให้หน้าต่าง “เตรียมแอปให้พร้อมใช้” เปิดขึ้นกลางเทสต์อื่น

## 11. Dev bridge

`crates/devbridge` เปิด `api::dispatch` ตัวเดียวกันผ่าน HTTP ที่ `127.0.0.1:1421` (CORS เฉพาะ `http://localhost:1420`)
ให้ UI ที่รันด้วย `pnpm dev` ในเบราว์เซอร์ทำงานกับ Rust และคลังทดสอบจริง จึงไม่ต้องมี mock data ฝั่ง UI
เป็น binary แยกที่ `src-tauri` ไม่ได้อ้างถึง จึงไม่อยู่ในแอปที่แจก ในโหมดนี้ไม่มี native picker: UI ใช้ช่องพิมพ์ path ที่ติดป้าย "โหมดพัฒนา"

วิธีใช้กับตัววิเคราะห์ใบหน้า (สิ่งที่เคยทำให้เสียเวลา):

- **วัดความเร็วด้วย release เท่านั้น** — `cargo build --release -p puri-devbridge` แล้วรัน `target/release/puri-devbridge`; debug ช้ากว่าราว 5 เท่าในขั้นใบหน้า
- ตั้ง `PURI_DATA_DIR=<โฟลเดอร์ทิ้งได้> PURI_DISABLE_OPEN=1` เสมอ; อย่าเปิดกับคลังจริงของผู้ใช้
- ไม่ให้ดาวน์โหลดโมเดล 289 MB ทุกรอบ: เก็บ `buffalo_l.zip` (release v0.7 ของ InsightFace, 288,621,354 bytes) ไว้ในเครื่อง แล้วตั้ง `PURI_MODEL_URL=file:///path/buffalo_l.zip`
- port 1421 ตายตัว: `pkill -f puri-devbridge` ตัวเก่าและรอให้ port ว่างก่อนเปิดตัวใหม่ ไม่งั้นตัวใหม่ panic ตอน bind
- ทดสอบตัววิเคราะห์จริงในหน้าต่าง Tauri: ตั้ง `PURI_E2E_SCRIPT` เป็นสคริปต์ของตัวเองแล้วรัน `pnpm tauri dev` (อย่าตั้ง `PURI_DISABLE_FACE_ENGINE` ซึ่ง `e2e/run.sh` ตั้งไว้)

## 12. แพลตฟอร์ม

พัฒนาและทดสอบด้วยมือบน macOS 26.7 / Apple M4 (arm64) / Rust 1.99.1 เท่านั้น Intel Mac: compile ผ่าน ไม่เคยรัน

**Windows** (เจ้าของผลิตภัณฑ์สั่งทำ 18 พ.ย. 2569): build และรันได้บน x64 แต่**ไม่มีเครื่อง Windows ของเราเอง** — ที่เดียวที่โค้ดฝั่ง Windows ถูกรันคือ
job `windows` ใน `ci.yml` (runner ของ GitHub) ซึ่งรันเทสต์ Rust ทั้งชุด, `e2e/run.sh` ในหน้าต่าง WebView2 จริง และตัววิเคราะห์ใบหน้ากับโมเดลจริง
- ตัวติดตั้งเป็น NSIS (`src-tauri/tauri.windows.conf.json`) แบบติดตั้งต่อผู้ใช้ **ไม่ได้เซ็น** (ไม่มีใบรับรอง Authenticode) SmartScreen จึงเตือน
- ติดตั้งโมเดลใช้ `curl.exe` + `tar.exe` (bsdtar) ใน `System32` ซึ่งมีตั้งแต่ Windows 10 รุ่น 1803 เรียกด้วย path เต็มเพื่อไม่ขึ้นกับ `PATH` ของผู้ใช้
  (GNU tar ของ Git แตก zip ไม่ได้) และตั้ง `CREATE_NO_WINDOW` ไม่ให้หน้าต่าง console เด้ง
- `std::fs::canonicalize` ของ Windows คืน path รูป `\\?\C:\…` ซึ่ง Explorer ไม่รับ: `util::canonical` ตัดคำนำหน้าออกก่อนเก็บลงคลัง
- คำนำหน้าโฟลเดอร์ในฐานข้อมูลใช้ตัวคั่นของระบบ (`MAIN_SEPARATOR`) — เดิมเขียน `/` ตายตัว ทำให้ตรวจโฟลเดอร์ซ้อนกันผิดบน Windows (เทสต์ T04 จับได้)
- เปิดไฟล์ต้นฉบับผ่าน `explorer <path>` ไม่ผ่าน `cmd /C start` (ไม่ต้อง escape ชื่อไฟล์ และไม่ผ่าน shell)
- คลังที่สร้างบนระบบหนึ่งไม่ได้ออกแบบให้ย้ายไปเปิดอีกระบบ (path ของรูปต่างรูปแบบกัน) — ยังไม่มีการเชื่อมตำแหน่งโฟลเดอร์ใหม่ (S14)
- ไม่ทราบตำแหน่งฐานข้อมูลของรุ่น Python บน Windows: การนำรายชื่อจากรุ่นเดิมเข้าจึงใช้ได้เฉพาะ macOS
- ไม่มี build สำหรับ Windows บน ARM และ Linux

## 13. อัปเดตแอปเอง

เจ้าของผลิตภัณฑ์สั่งทำ 19 พ.ย. 2569: "เผื่อออกเวอร์ชั่นใหม่ ๆ คนเค้าจะได้แอปที่อัพเดทตลอดเวลา" ใช้ `tauri-plugin-updater` 2.14

- **พฤติกรรม:** ตรวจเอง 5 วินาทีหลังเปิดแอปและทุก 6 ชั่วโมง → พบรุ่นใหม่แล้วดาวน์โหลดเบื้องหลังทันที → ตรวจลายเซ็น → ขึ้นปุ่มในเมนูซ้ายและ toast หนึ่งครั้ง
  → **ติดตั้งเมื่อผู้ใช้กดเท่านั้น** (แอปต้องปิดและเปิดใหม่ งานเบื้องหลังหยุดที่ขอบรายการเหมือนตอน Quit) ไม่ติดตั้งเองตอนปิดแอป:
  บน Windows การติดตั้งคือการรันตัวติดตั้ง NSIS ซึ่งทดสอบได้เฉพาะบน runner จึงไม่ให้เกิดโดยผู้ใช้ไม่ได้สั่ง ผลคือคนที่ไม่กดปุ่มจะค้างรุ่นเดิม (ปุ่มกลับมาทุกครั้งที่เปิดแอป)
  ไฟล์ที่ดาวน์โหลดเก็บในหน่วยความจำ (~20 MB) ปิดแอปก่อนกดติดตั้ง = ดาวน์โหลดใหม่ครั้งหน้า
- **ไปรุ่นล่าสุดในครั้งเดียว (20 พ.ย. 2569 — เจ้าของผลิตภัณฑ์เจอแอปเสนอ alpha.7 ทั้งที่ออก alpha.8 แล้ว):** เดิมเมื่อดาวน์โหลดรุ่นใหม่เสร็จ
  แอปหยุดถามเซิร์ฟเวอร์จนกว่าจะติดตั้ง รุ่นที่ออกทีหลังจึงไม่ถูกเห็น ตอนนี้ระหว่างรอผู้ใช้กด แอปยังถามตามรอบเดิมแบบเงียบ ๆ
  พบรุ่นที่ใหม่กว่า → ดาวน์โหลดรุ่นนั้นแทน (ปุ่มติดตั้งหายไประหว่างดาวน์โหลด) ถ้าดาวน์โหลดหรือตรวจลายเซ็นไม่ผ่าน กลับไปเสนอรุ่นที่ถือไว้ตามเดิม
- **ที่อยู่ของตรรกะ:** `src-tauri/src/updater.rs` (ไม่ใช่ `crates/core` — เป็นเรื่องของเปลือกแอป ไม่ใช่ข้อมูลคลัง) เปิดสามคำสั่ง `update_status` / `update_check` /
  `update_install` + event `update-status`; web view **ไม่ได้รับ**สิทธิ์ของ plugin (`capabilities/default.json` ไม่เปลี่ยน) และ UI เป็นผู้จับเวลาเอง
  ค่า "ตรวจและดาวน์โหลดให้เอง" เก็บใน localStorage เหมือนธีม (ค่าเริ่มต้น เปิด)
- **manifest อยู่บน branch `updates`** (`latest.json` ผ่าน `raw.githubusercontent.com`) ไม่ใช่ `releases/latest/download/…`:
  ทุกรุ่นของเรายังเป็น pre-release ซึ่ง GitHub ไม่นับเป็น "latest" ลิงก์นั้นจึงไม่มีวันชี้มาที่รุ่น alpha ผลข้างเคียง: มี manifest ชุดเดียว
  **ยังไม่มีช่องทางแยก stable / ทดลอง** — เมื่อมีรุ่นจริงแล้วออก beta ต่อ ผู้ใช้รุ่นจริงจะถูกชวนไป beta ด้วย ต้องแยกช่องทางก่อนถึงวันนั้น
- **ลายเซ็น:** กุญแจ minisign ของตัวอัปเดต (ไม่มีรหัสผ่าน — ตัวไฟล์คือความลับ) สร้าง 19 พ.ย. 2569 เก็บที่ `~/.config/puriphotosearch/updater.key` บน Mac ของเจ้าของ
  workflow ใช้ผ่าน secret `TAURI_SIGNING_PRIVATE_KEY` ที่เจ้าของตั้งเองจากไฟล์นั้น; กุญแจสาธารณะอยู่ใน `tauri.conf.json` ตั้ง `requireSignedVersion` — ลายเซ็นผูกกับเลขรุ่น
  manifest ที่ถูกแก้จึงจับคู่เลขรุ่นใหม่กับไฟล์รุ่นเก่า (ที่เซ็นถูกต้อง) เพื่อบังคับถอยรุ่นไม่ได้ กุญแจหาย = แอปที่แจกไปอัปเดตเองไม่ได้อีก
- **`createUpdaterArtifacts` ไม่อยู่ใน `tauri.conf.json`** แต่ส่งผ่าน `--config` เฉพาะตอนมีกุญแจ (workflow `Release`, `scripts/release-mac.sh`, `e2e/update.sh`)
  ไม่งั้น `pnpm tauri build` ธรรมดา (CI, e2e, เครื่องของผู้ร่วมพัฒนา) จะล้มเพราะไม่มีกุญแจส่วนตัว
- **ไฟล์อัปเดต:** macOS = `.app` ที่เซ็น + notarize แล้วห่อเป็น `PuriPhotoSearch-mac.app.tar.gz` (universal ไฟล์เดียวใช้ทั้งสองชิป; ตัวอัปเดตสลับ bundle ในที่เดิม
  ถ้าไม่มีสิทธิ์เขียน macOS จะถามรหัสผู้ดูแลเครื่อง) · Windows = ตัวติดตั้ง NSIS ตัวเดียวกับที่ให้ดาวน์โหลด รันแบบ passive แล้วเปิดแอปให้ใหม่
- **Windows ทดสอบใน workflow `Release`** (job `update-windows`): ไม่มีเครื่องของเราเอง จึงให้ runner ติดตั้งรุ่นปัจจุบันด้วยตัวติดตั้งจริง แล้วให้แอปอัปเดตตัวเอง
  ทุกครั้งที่ออกรุ่นหรือซ้อม job นี้ทดสอบ debug build ของ commit นั้นกับกุญแจชั่วคราว ไม่ใช่ไฟล์ของ release และไม่ขวางการเผยแพร่
  บน macOS เทสต์เดียวกัน (`e2e/update.sh`) ต้องมี window server จึงรันในเครื่องเท่านั้น
- **หลังออกรุ่น พิสูจน์ด้วยไฟล์ที่เผยแพร่จริงทั้งสองฝั่ง** (`e2e/update-published.sh`): release build ไม่มี hook ของเทสต์ สคริปต์จึงกดปุ่มในหน้าต่าง
  ผ่าน Accessibility ของ macOS (`e2e/ax.swift`) เหมือนที่ผู้ใช้กด — ไม่เพิ่มช่องทางพิเศษใด ๆ ในแอปที่แจก
- **debug build ไม่ตรวจหารุ่นใหม่** (หน้าตั้งค่าบอกตามจริงว่าเป็นรุ่นสำหรับพัฒนา) เว้นแต่ตั้ง `PURI_UPDATE_ENDPOINT` ซึ่ง `e2e/update.sh` ใช้ชี้ไปที่ manifest ในเครื่อง;
  release ไม่มีโค้ดส่วนนี้ และ plugin รับปลายทางเฉพาะ `https`
- **ข้อความ "มีอะไรใหม่"** มาจาก `docs/release-notes/<เลขรุ่น>.md` ที่เขียนใน PR ปรับเลขรุ่น แสดงเป็นข้อความธรรมดา (ไม่มีตัวแปลง Markdown ในแอป)
- คลังที่รุ่นใหม่ต้องยกระดับ schema ถูกสำรองก่อนเสมอ (ชุด `before_upgrade` ของข้อสำรองข้อมูล) — การอัปเดตเองไม่ได้เพิ่มความเสี่ยงต่อข้อมูลจากการติดตั้งทับด้วยมือ

## 14. ส่งออกแบบย่อขนาด (20 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ หลังเทียบกับ PuriSlim)

- **อยู่ในหน้าต่างส่งออก ไม่ใช่เครื่องมือแยก:** ปลายทางของแอปคือหาคน → เลือกรูป → ส่งต่อ การย่อจึงเป็นตัวเลือก "ขนาดของสำเนา"
  (ต้นฉบับ · ด้านยาว 2048/1600/1080 · กำหนดด้านยาวเอง · ขนาดไฟล์ไม่เกิน) ค่าเริ่มต้นยังเป็นต้นฉบับ และจำค่าล่าสุดไว้ในเครื่อง
- **ไม่แตะต้นฉบับ:** ไม่มีตัวเลือก "บันทึกทับ" แบบ PuriSlim · ไม่มี "ยืด" (หน้าคนเบี้ยว) · ไม่มีหน้าต่างครอปทีละรูป (ไม่เข้ากับการส่งออกหลายร้อยใบ)
- **ย่อเฉพาะรูปที่ใหญ่กว่าที่ขอ:** รูปที่เล็กพออยู่แล้วคัดลอกไฟล์เดิมทุกไบต์ · ตัดสินจากข้อมูล revision ชุดเดียวกันทั้งตอนวางแผนและตอนทำ
  นามสกุลที่วางแผนไว้จึงตรงกับไฟล์ที่เขียนเสมอ · สำเนาที่ย่อเป็น JPEG คุณภาพ 90 (PNG → `.jpg` ปูพื้นขาวใต้ส่วนโปร่งใส)
- **ขนาดไฟล์ไม่เกิน:** แนวทางเดียวกับ PuriSlim — ลดขนาดภาพโดยคงคุณภาพ 90 แล้วไล่คุณภาพขึ้นถึง 95 ให้เต็มงบ (คมกว่ากดคุณภาพลงอย่างเดียว)
  แต่เดาขนาดภาพแรกจากไบต์ต่อพิกเซล (0.22 ที่คุณภาพ 90 — วัดจากรูปกิจกรรมจริง) ไม่ใช่จากขนาดไฟล์ต้นฉบับ เพราะกล้องบีบอัดต่างกันหลายเท่า
  (เดาจากขนาดไฟล์ทำให้ช้า 3–9 วินาทีต่อรูป 43 ล้านพิกเซล) แล้วค้นในช่วง [ด้านที่พอดี, ด้านที่เกินงบ] · KB/MB ฐาน 1024 ตรงกับที่แอปแสดง
- **เก็บ metadata:** PuriSlim ทิ้ง EXIF ทั้งหมด วันถ่ายจึงหายเมื่อนำไปเปิดในแอปอื่น — ของเราย้าย segment EXIF และโปรไฟล์สี (ICC) ของต้นฉบับมาทั้งชุด
  แก้ Orientation เป็น 1 เพราะภาพหมุนตั้งตรงแล้ว (ภาพย่อใน EXIF และขนาดพิกเซลใน EXIF อาจไม่ตรงกับสำเนา — ยอมรับ) ไม่คัด XMP
  · เวลาแก้ไขไฟล์ของสำเนาเท่าต้นฉบับ · ถ้า EXIF ใหญ่เกินหนึ่งในสี่ของขนาดไฟล์ที่ขอ ตัด metadata ออกแทนการย่อภาพจนเสีย
- **ทำพร้อมกันได้ 4 รูป:** การย่อใช้ CPU มาก งานส่งออกจึงทำทีละชุด (จำกัด 4 เพื่อคุมหน่วยความจำของภาพที่ถอดรหัสค้างไว้) ฐานข้อมูลอ่าน/เขียนในเธรดงานเท่านั้น
  · หยุด/ยกเลิกมีผลหลังชุดที่กำลังทำ
- **schema v3:** เพิ่ม `export_runs.resize` (วิธีย่อของงาน) และ `export_items.output_bytes` (รายงานว่าลดไปเท่าไร) — คลังที่เปิดด้วยรุ่นนี้
  จะเปิดด้วยรุ่นก่อนหน้าไม่ได้อีก (`LIBRARY_TOO_NEW`) แอปสำรองคลังเดิมก่อนอัปเกรดเอง (หมวด 8.4) เลือกเพิ่มคอลัมน์แทนการเก็บในตารางอื่น
  เพราะเป็นข้อมูลของงานส่งออกโดยตรง

## 15. ย่อไฟล์ต้นฉบับในที่เดิม (20 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ และเลือกให้ต้นฉบับไปถังขยะ)

ข้อยกเว้นเดียวของ "ไม่แก้ไฟล์ต้นฉบับ" (AGENTS.md ข้อ 1) เพื่อคืนพื้นที่ดิสก์ของคลังรูปกิจกรรม — ทำเมื่อผู้ใช้เลือกรูป กด "ย่อไฟล์ต้นฉบับ"
ตรวจแผน และติ๊ก "เข้าใจแล้ว" เท่านั้น

- **ข้อมูลใบหน้าอยู่ครบโดยไม่สร้าง revision ใหม่:** กรอบใบหน้าเก็บเป็นสัดส่วน 0–1 บนภาพที่หมุนตั้งตรงแล้ว ไฟล์ที่ย่อก็หมุนตั้งตรง (Orientation = 1)
  กรอบเดิมจึงตรงตำแหน่ง แอปจึงปรับขนาด/hash/ขนาดภาพของ revision เดิม แทนที่ตัวสแกนจะเห็นไฟล์เปลี่ยนแล้วสร้าง revision ใหม่
  (ซึ่งทำให้ต้องวิเคราะห์ใหม่ และคำยืนยัน/คำปฏิเสธค้างอยู่กับ revision เก่า) — ภาพย่อใน cache และครอปใบหน้าก็ใช้ต่อได้
  · ย่อไฟล์ด้วยโปรแกรมอื่นแล้วสแกนใหม่ยังเป็นแบบเดิม (revision ใหม่) เพราะแอปพิสูจน์ไม่ได้ว่าเป็นภาพเดิม
- **ด้านยาวไม่ต่ำกว่า 1280 px:** ตัววิเคราะห์ใบหน้าย่อรูปเหลือด้านยาว 1280 ก่อนวิเคราะห์อยู่แล้ว (`puri_faces::MAX_IMAGE_DIM`)
  วิเคราะห์ใหม่ภายหลังจึงได้ผลเท่ากับต้นฉบับ — ตัวเลือก 1080 ไม่มีในงานนี้ · ขนาดไฟล์ไม่ต่ำกว่า 300 KB และรูปที่ต้องย่อจนต่ำกว่า 1280 ถูกข้าม
  · มี `const assert` ใน crate faces กันค่าสองตัวนี้คลาดกัน
- **ต้นฉบับไปถังขยะ ไม่ลบ:** macOS ใช้ `NSFileManager trashItemAtURL` (ไม่ผ่าน Finder: ไม่ต้องขอสิทธิ์ควบคุม Finder ไม่มีเสียงทุกรูป
  และได้ตำแหน่งในถังขยะกลับมาเก็บไว้) · Windows ใช้ crate `trash` และยอมเฉพาะไดรฟ์ชนิด fixed เพราะไดรฟ์เครือข่ายและแฟลชไดรฟ์ USB
  ไม่มีถังขยะ (ระบบจะลบถาวร) — ที่ที่ย้ายไปถังขยะไม่ได้ รูปนั้น "ไม่สำเร็จ" และไฟล์อยู่ที่เดิม · พื้นที่คืนเมื่อผู้ใช้ล้างถังขยะเอง
- **เฉพาะ JPEG:** PNG ต้องเปลี่ยนนามสกุลเป็น `.jpg` (เปลี่ยนชื่อไฟล์ของผู้ใช้) จึงข้าม · ทางลัด (symlink) ข้าม
- **ไม่แทนเมื่อไม่คุ้มหรือเสียข้อมูล:** ไฟล์ที่ย่อต้องเล็กลงอย่างน้อย 10% และต้องมี segment EXIF/ICC ครบเท่าต้นฉบับ (โหมดขนาดไฟล์อาจตัด EXIF
  ทิ้งเมื่องบเล็กมาก — ยอมได้กับสำเนา แต่ไม่ยอมกับต้นฉบับ) · เวลาแก้ไขไฟล์ สิทธิ์ไฟล์ และ (macOS) ป้ายสี/ข้อมูลเสริมของ Finder เท่าเดิม
  · วันที่สร้างไฟล์ (birth time) เป็นเวลาที่ย่อ — ยอมรับ
- **แอปปิดหรือไฟดับตรงไหนก็ไม่มีรูปหาย:** ต่อรูปเรียงขั้น — จดตำแหน่งไฟล์ชั่วคราว → เขียนไฟล์ที่ย่อข้างต้นฉบับ (`.puri-shrink-*.part`)
  แล้วอ่านกลับมาตรวจ hash → จด `replacing` + hash → ต้นฉบับไปถังขยะ → เปลี่ยนชื่อไฟล์ชั่วคราวเป็นชื่อเดิม → ปรับ revision + `shrunk`
  ใน transaction เดียว · `shrink::recover` ทำงานตอนเปิดคลังก่อน worker เริ่มสแกน: ดูสภาพไฟล์จริงแล้วทำต่อหรือคืนเข้าคิว
  (ไฟล์ชั่วคราว + ต้นฉบับอยู่ → ลบไฟล์ชั่วคราว คืนเข้าคิว · ไฟล์ชั่วคราวอยู่ ต้นฉบับไม่อยู่ → วางไฟล์ที่ย่อ · ไฟล์ที่อยู่ตรง hash → บันทึก)
  · ห้ามลบไฟล์ชั่วคราวของรายการที่ถึงขั้น `replacing` แล้ว เพราะอาจเป็นไฟล์ที่ย่อชุดเดียวที่มีขณะต้นฉบับอยู่ในถังขยะ
- **schema v4:** ตาราง `shrink_runs` / `shrink_items` (สถานะต่อรูป เหตุผลที่ข้าม ตำแหน่งในถังขยะ) · `jobs.kind` เพิ่ม `shrink`
  (สร้างตารางใหม่แบบเดียวกับ v2) · `export_items.source_bytes` ให้รายงานส่งออกเก่ายังบอกขนาดต้นฉบับถูกแม้ต้นฉบับถูกย่อภายหลัง
  · ออกพร้อม v3 ในรุ่นเดียวกัน (2.0.0-alpha.11) จึงสำรองคลังครั้งเดียวตอนอัปเกรด

## 16. ลายน้ำของสำเนาที่ส่งออก (20 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ ขั้นที่ 2 หลังเทียบกับ PuriSlim)

- **เฉพาะสำเนาที่ส่งออก:** ไม่มีในหน้าต่าง "ย่อไฟล์ต้นฉบับ" — ลายน้ำที่ฝังลงต้นฉบับเอาออกไม่ได้อีก
- **โลโก้เป็นรูป (PNG พื้นใส หรือ JPEG) แบบเดียวกับ PuriSlim ยังไม่มีลายน้ำแบบพิมพ์ข้อความ:** การวาดอักษรไทยให้สระและวรรณยุกต์ซ้อนถูกต้อง
  ต้องมีตัวจัดรูปอักษร (shaping) และฟอนต์ไทยติดแอป ซึ่งยังไม่คุ้มเมื่อทำข้อความเป็น PNG มาใช้ได้ · JPEG ใช้ได้แต่แอปเตือนว่าจะเห็นเป็นกรอบสี่เหลี่ยม
- **เก็บโลโก้ในคลัง (schema v5 ตาราง `watermarks`, PNG ด้านยาวไม่เกิน 2048):** ไม่ต้องตามไฟล์ข้างนอก ชุดสำรองของคลังมีครบ
  ไฟล์ต้นทางไม่ถูกแตะ · ลบได้ด้วยกล่องยืนยันของแอป · งานส่งออกเก็บค่าที่เลือก (`export_runs.watermark`) ถ้าโลโก้ถูกลบก่อนงานทำ
  งานหยุดรอพร้อมเหตุผล ไม่ส่งออกสำเนาที่ไม่มีลายน้ำแทนโดยไม่บอก
- **ตำแหน่ง ขนาด ความทึบ เท่า PuriSlim:** เก้าตำแหน่ง · ด้านยาวของโลโก้ = ด้านสั้นของภาพ × ขนาด (5–100%, เริ่มต้น 25%) · ขอบ 3% ของด้านสั้น
  · ความทึบ 5–100% (เริ่มต้น 80%) · วาดหลังย่อและหมุนแล้ว ลายน้ำจึงดูสัดส่วนเท่ากันทุกรูปและทุกขนาดสำเนา
- **ตัวอย่างในหน้าต่างใช้สูตรเดียวกับ Rust:** `watermarkRect` (TS) กับ `media::watermark_rect` มีเทสต์ค่าเดียวกันทั้งสองฝั่ง ตัวอย่างวางโลโก้ทับรูปแรก
  ที่เลือกด้วย CSS จึงเปลี่ยนทันทีที่เลื่อนแถบ ไม่ต้องให้ Rust สร้างภาพตัวอย่าง
- **ย่อโลโก้แบบ premultiplied alpha:** ไม่มีขอบดำรอบส่วนโปร่งใส · ภาพขาวดำที่ใส่ลายน้ำสีกลายเป็นภาพสี จึงไม่คัดโปรไฟล์สีแบบขาวดำมา
- **ใส่ลายน้ำ = บันทึกใหม่ทุกรูป:** แม้เลือก "ขนาดเดิม" ก็บันทึกเป็น JPEG คุณภาพ 90 (ไฟล์มักเล็กลงจากต้นฉบับของกล้อง) PNG กลายเป็น `.jpg`
  — ตัวเลือก "ต้นฉบับ (คัดลอกไฟล์เดิม)" จึงเปลี่ยนชื่อเป็น "ขนาดเดิม (ไม่ย่อ)" และคำอธิบายเปลี่ยนตามเมื่อเปิดลายน้ำ

## 17. แต่งภาพแบบไม่แตะไฟล์ (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์เลือก "เก็บในแอปแบบ Lightroom")

แผนทั้งชุด: (1) ตัด/หมุน/ปรับเอียง (2) แสงและสี (3) คัดลอก/วางการแต่งให้หลายรูป (4) preset ของผู้ใช้ + นำเข้า preset `.xmp` ของ Lightroom
— ข้อนี้บันทึกขั้นที่ 1 และฐานที่ขั้นอื่นใช้ร่วม

- **เก็บค่าที่แต่ง ไม่เขียนไฟล์:** ตาราง `photo_edits` (schema v6) หนึ่งแถวต่อรูป เก็บ JSON ของ `edit::EditSettings` · ไฟล์ต้นฉบับไม่ถูกแตะ
  (กฎข้อ 1 ใน AGENTS.md ยังเหมือนเดิม) · แต่งซ้ำ เปลี่ยนใจ หรือ "กลับเป็นภาพต้นฉบับ" ได้ทุกเมื่อโดยไม่เสียคุณภาพ · ข้อเสีย: โปรแกรมอื่นเห็นรูปเดิม
  ได้รูปที่แต่งจากการส่งออก (เจ้าของผลิตภัณฑ์ยอมรับ)
- **ลำดับเดียวกับ Lightroom:** หมุนตาม EXIF → หมุนทีละ 90° → ปรับเอียง ±45° (กรอบหลังเอียง = สี่เหลี่ยมสัดส่วนเดิมที่ใหญ่สุดในภาพที่เอียง
  จึงไม่มีมุมว่าง) → ตัด (สัดส่วนของกรอบหลังเอียง) · ไม่เอียง = ตัดตามพิกเซลตรง ๆ ไม่สุ่มสีใหม่ · เอียง = bilinear
- **ใบหน้าเก็บบนภาพเดิมเสมอ:** การแต่งไม่เปลี่ยนแถวใบหน้า เวกเตอร์ คำยืนยัน หรือคำปฏิเสธ · ตอนแสดง `faces::for_revision_with_suggestions`
  แปลงกรอบไปยังภาพที่แต่ง (`edit::Geometry::map_box`: กรอบตั้งตรงที่ครอบมุมทั้งสี่ของกรอบที่หมุน) · กรอบที่วาดบนภาพที่แต่งแปลงกลับก่อนเก็บ
  (`unmap_box`) · ใบหน้าที่เหลือในภาพไม่ถึงครึ่ง = `outsideCrop` ไม่วาดบนภาพ แต่ยังอยู่ในรายการคนในรูป **และยังนับว่าคนนั้นอยู่ในรูปนี้ตอนค้นหา**
  (ต้นฉบับยังมีคนนั้นอยู่ ย้อนการตัดได้ — ไม่ซ่อนจากผลค้นหาโดยไม่บอก) · ภาพครอปใบหน้ายังมาจากต้นฉบับ
- **ภาพที่แต่งสร้างเมื่อใช้ เก็บใน cache ตาม `edit_id`:** ภาพย่อ 512 px และภาพสำหรับตัวดูภาพด้านยาวไม่เกิน 2560 px (`cache/edits/`)
  ถอดรหัสต้นฉบับเท่าที่ต้องใช้ · `edit_id` ใหม่ทุกครั้งที่บันทึก จึงไม่มีวันได้ภาพเก่า และลบไฟล์ของครั้งก่อนทิ้ง · ต้นฉบับไม่พร้อม = แต่งจากภาพย่อเดิม
  · UI ใช้ `editId` เป็นรุ่นของ URL ภาพ · asset `original/{id}` = ไฟล์ต้นฉบับเสมอ (หน้าแต่งภาพใช้)
- **ส่งออก = ภาพที่แต่ง:** ทุกรูปที่แต่งถูกบันทึกใหม่ (เหมือนใส่ลายน้ำ) ตัด/หมุนก่อนย่อและก่อนลายน้ำ ถอดรหัสเผื่อส่วนที่ถูกตัดออก · ย่อไฟล์ต้นฉบับ
  ไม่เกี่ยวกับการแต่ง (ค่าที่แต่งเป็นสัดส่วน ใช้ต่อได้หลังย่อ)
- **หน้าแต่งภาพแสดงด้วย CSS:** รูปต้นฉบับหมุน `rotate + straighten` องศาในกล่องสัดส่วนของกรอบ (ตัดขอบเฉพาะชั้นภาพ ชั้นกรอบตัดอยู่นอกเพื่อให้ที่จับไม่ถูกตัด)
  คณิตใน `editGeometry.ts` สูตรเดียวกับ Rust (เทสต์ค่าเดียวกันทั้งสองฝั่ง) · ใบหน้าที่จะหลุดกรอบเป็นกรอบแดงพร้อมคำเตือนก่อนบันทึก

## 18. แต่งภาพ ขั้นที่ 2: แสงและสี (21 พ.ย. 2569)

- **แถบปรับชุดเดียวกับที่คนคุ้นจาก Lightroom แบบย่อ:** ค่าแสง (±3 EV) คอนทราสต์ ส่วนสว่าง เงา จุดขาว จุดดำ อุณหภูมิสี โทนสี ความสดของสี ความอิ่มสี
  (±100) · ดับเบิลคลิกชื่อหรือแถบ = คืนเป็น 0 · ปุ่มกดค้างดูก่อนปรับ · เก็บใน `EditSettings.adjust` (แถวเดิมของ `photo_edits` ไม่ต้องเปลี่ยน schema)
- **ไม่ใช่สูตรของ Adobe:** Adobe ไม่เปิดสูตร — ของเราเป็นสูตรที่อธิบายได้และทดสอบได้ (`adjust.rs`): สมดุลแสงขาวและค่าแสงทำในแสงเชิงเส้น
  แล้วจุดดำ/ขาว (levels) เงา/ส่วนสว่าง (เส้นน้ำหนักที่ปลายสองข้างไม่ขยับ) คอนทราสต์ (S-curve) รวมเป็นตาราง 256 ค่าต่อช่อง แล้วจึงความอิ่ม/ความสดของสีต่อพิกเซล
  · ผลจึงใกล้เคียงทิศทางเดียวกับ Lightroom แต่ไม่เท่ากันทุกพิกเซล (จะสำคัญตอนนำเข้า preset .xmp ในขั้นที่ 4)
- **ตัวอย่างสดตรงกับไฟล์ที่ได้:** หน้าแต่งภาพวาดลง canvas (`adjust.ts` สูตรเดียวกัน — เทสต์ค่าเดียวกันทั้งสองฝั่งได้ตรงทุกพิกเซล) จากภาพต้นฉบับที่ย่อเหลือ
  2400 px ครั้งเดียว · วาดหนึ่งครั้งราว 30 ms ที่จอ 1440×900 · ภาพย่อ ตัวดูภาพ และสำเนาที่ส่งออกสร้างด้วย Rust
- **ปรับอัตโนมัติแบบระวัง:** ภาพแรกที่ลองตั้งค่าแสงเป้าหมายตายตัว 45% ทำให้ภาพห้องโถงสว่างหม่นลง −0.9 EV จึงเปลี่ยนเป็นแตะค่าแสงเฉพาะเมื่อค่ากลางความสว่าง
  ต่ำกว่า 30% หรือสูงกว่า 62% (ไม่เกิน ±1 EV) แล้วยืดจุดดำ/ขาวจากฮิสโตแกรมหลังปรับค่าแสง (ไม่เกิน ±60) · ไม่แตะสี
- **แต่งแค่แสงสีไม่แปลงกรอบใบหน้า** (ตำแหน่งเท่าเดิม — กันเศษทศนิยมสะสม)

## 19. แต่งภาพ ขั้นที่ 3: คัดลอกและวางการแต่งให้หลายรูป (21 พ.ย. 2569)

- **แบบ Copy/Paste Settings ของ Lightroom:** เมนู ⋮ ในตัวดูภาพ "คัดลอกการแต่ง" (เก็บในหน่วยความจำจนปิดแอป) → เลือกรูปกี่รูปก็ได้
  (รวม "เลือกผลทั้งหมด") → ปุ่ม "วางการแต่ง" ในแถบเลือกรูป หรือเมนู ⋮ ของรูปเดียว
- **เลือกส่วนที่จะวาง:** แสง (ค่าแสง คอนทราสต์ ส่วนสว่าง เงา จุดขาว จุดดำ) · สี (อุณหภูมิ โทนสี ความสด ความอิ่ม) · ตัด/หมุน/ปรับเอียง
  — ค่าเริ่มต้นไม่ติ๊กตัด/หมุน (แต่ละรูปจัดองค์ประกอบต่างกัน) และเตือนเมื่อติ๊ก · ส่วนที่ไม่ได้เลือกของแต่ละรูปคงเดิม (`EditParts::merge`)
  · ติ๊กส่วนที่รูปต้นทางไม่ได้แต่ง = ล้างส่วนนั้นของรูปที่เลือก (บอกไว้ในหน้าต่าง)
- **เก็บค่าอย่างเดียวในหนึ่ง transaction:** ไม่ต้องสร้างภาพทันที (ภาพย่อที่แต่งสร้างเมื่อถูกเปิดดู) จึงวางให้หลายพันรูปได้ทันที · รูปที่ยังไม่รู้ขนาดภาพถูกข้ามและนับแจ้ง
  · ได้ค่าเดิมอยู่แล้ว = ไม่เขียนซ้ำ (ภาพใน cache ไม่ถูกทิ้งโดยไม่จำเป็น)

## 20. แต่งภาพ ขั้นที่ 4: preset และนำเข้า preset ของ Lightroom (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ "เอา profile ของ lightroom มาใส่ได้" และ "บันทึกเป็น preset ได้หลายอัน")

- **preset = ค่าแสงและสีชุดหนึ่ง** (ไม่รวมการตัด/หมุน — แต่ละรูปจัดองค์ประกอบต่างกัน) เก็บในตาราง `edit_presets` (schema v7) · บันทึกจากค่าปัจจุบัน
  ตั้งชื่อได้ เปลี่ยนชื่อ ลบ · ลบ preset แล้วรูปที่ใช้ไปไม่เปลี่ยน (ค่าเก็บกับรูปเอง) · แท็บ "Preset" ในหน้าแต่งภาพ: ชี้เพื่อดูตัวอย่างบนภาพ
  คลิกเพื่อใช้ · **ใช้ preset = แทนค่าแสงและสีทั้งหมดของรูปนั้น** (Lightroom แตะเฉพาะค่าที่อยู่ใน preset — ของเราเรียบกว่าและคาดเดาได้ เพราะ preset
  ที่นำเข้าเก็บครบทุกค่า) · รายการเรียงแบบพจนานุกรมไทยที่ UI (`Intl.Collator('th')` — SQLite เรียงตาม byte ทำให้คำที่ขึ้นต้นด้วยสระนำไปอยู่ท้าย)
- **ขยายตัวแต่งให้รองรับสิ่งที่ preset จริงใช้:** preset สามไฟล์ของเจ้าของผลิตภัณฑ์ใช้ HSL ต่อช่วงสี เส้นโค้งโทนแบบจุด และ Parametric curve
  นอกจากแถบพื้นฐาน จึงเพิ่มสามอย่างนี้ใน `Adjust` (ค่าเดิมที่ไม่มีช่องใหม่อ่านได้ด้วย `serde(default)`):
  HSL 8 ช่วงสีแบบ Lightroom (เฉดสี ±30° · ความอิ่ม · ความสว่าง — ผลแรงตามความอิ่มของพิกเซล สีเทาไม่เปลี่ยน) ·
  เส้นโค้งแบบจุด (monotone cubic ไม่แกว่งเกินจุด) ทั้งรวมและแยกช่องแดง/เขียว/น้ำเงิน · Parametric 4 ช่วง + จุดแบ่ง ·
  ปรับ HSL และ Parametric ด้วยแถบได้ · **เส้นโค้งแบบจุดแก้ในแอปไม่ได้** (แสดงเป็นกราฟ ล้างได้) — มาจาก preset เท่านั้น
- **นำเข้า .xmp อ่านเฉพาะสิ่งที่ทำได้ และบอกสิ่งที่ทำไม่ได้ตามจริง:** แถบพื้นฐาน (`*2012`) ความสด/ความอิ่ม HSL เส้นโค้ง Parametric
  สมดุลแสงขาวแบบเพิ่ม/ลด (`IncrementalTemperature/Tint` — preset ของ JPEG) · แบบ Kelvin ของ RAW แปลงโดยประมาณ · `As Shot` = ไม่ปรับ ·
  ขาวดำ → ความอิ่ม −100 · ส่วนที่ทำไม่ได้ (Profile, Texture, Clarity, Dehaze, Vignette, Grain, ลดนอยส์, Sharpening, Color Grading, Mask)
  เก็บเป็นรายการ "นำเข้าไม่ได้" แสดงทั้งตอนนำเข้าและในรายการ preset · ไฟล์ต้นทางไม่ถูกแตะ (อ่านอย่างเดียว ไม่เกิน 2 MB)
- **ผลใกล้เคียง Lightroom ไม่ใช่เท่ากัน:** สูตรของ Adobe ไม่เปิดเผย และ Profile/Texture/Clarity/Mask ที่ preset จริงใช้อยู่ทำไม่ได้
  — บอกผู้ใช้ไว้ในหน้าต่างนำเข้า · ยังไม่ได้เทียบภาพกับ Lightroom จริง (เครื่องนี้ไม่มี Lightroom)
- **ตัวอย่างสดยังตรงกับไฟล์ทุกพิกเซล:** สูตร HSL/เส้นโค้งใน `adjust.ts` เหมือน `adjust.rs` (เทสต์ค่าอ้างอิงชุดเดียวกัน) · ทาง HSL ต้องคำนวณต่อพิกเซล
  จึงเขียนแบบไม่สร้าง array ต่อพิกเซล (เร็วขึ้นราว 2 เท่า)
- **คัดลอก/วางการแต่ง (ข้อ 19):** ส่วน "แสง" รวมเส้นโค้งโทนและ Parametric · ส่วน "สี" รวม HSL
- **ใช้ preset กับหลายรูป:** ปุ่ม "ใช้ preset" ในแถบเลือกรูป (ขึ้นเมื่อมี preset แล้วเท่านั้น) → เลือก preset → แทนแสงและสีของทุกรูปที่เลือก
  กรอบตัด/หมุนของแต่ละรูปคงเดิม — ใช้ `apply_photo_edits` ตัวเดียวกับการวางการแต่ง (ส่วนแสง + สี)

## 21. เครื่องมือแต่งภาพละเอียดขึ้น: Levels, เส้นโค้งแบบลากจุด, Color Grading, Vignette, หลอดดูดสี (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ "ละเอียดเหมือน Lightroom ปรับ Level ปรับสีต่าง ๆ ได้ละเอียด" เพื่อให้ AI ใช้แทนได้ด้วย)

- **Levels แบบ Photoshop** (จุดดำ แกมมา จุดขาวของค่าเข้า + ดำสุด/ขาวสุดของค่าออก) ทั้งรวมทุกช่องและแยกช่องแดง/เขียว/น้ำเงิน · อยู่ในตาราง 256 ค่าต่อช่อง
  ถัดจาก Parametric: Levels รวม → เส้นโค้งรวม → Levels ของช่อง → เส้นโค้งของช่อง · แกมมาเลื่อนแบบลอการิทึม (กลางแถบ = 1.00)
- **เส้นโค้งแบบจุดแก้ได้ในแอป** แยกช่อง RGB/แดง/เขียว/น้ำเงิน: คลิกที่ว่างเพิ่มจุดบนเส้นเดิม ลากปรับ ดับเบิลคลิกลบ (ตรวจการกดสองครั้งเองจาก pointerdown
  — WebView ไม่ส่ง dblclick หลัง `preventDefault`) · เลือกจุดแล้วใช้ลูกศร (Shift = ทีละ 10) และ Delete ได้ · สูงสุด 16 จุดต่อช่องใน UI (คลังรับได้ 32)
- **Color Grading** เงา/ช่วงกลาง/ส่วนสว่าง/ทั้งภาพ (สี 0–360° ความเข้ม 0–100 ความสว่าง ±100) + Blending + Balance · วงล้อสีลากได้ (มุม = สี
  ระยะจากกลาง = ความเข้ม) พร้อมแถบตัวเลขให้ปรับละเอียด · สูตร: น้ำหนักรูประฆังตามความสว่างของพิกเซล เติมสีแบบไม่เปลี่ยนความสว่าง (หักค่า luma ของสีที่เติม)
  · ขั้นต่อพิกเซลหลัง HSL ก่อนความสด/ความอิ่ม
- **Vignette หลังตัด** (ปริมาณ จุดเริ่ม ความนุ่ม ความกลม) คิดตามตำแหน่งในกรอบภาพที่ได้: Rust ใส่หลังตัด/หมุนอยู่แล้ว · หน้าแต่งภาพใส่เฉพาะแท็บที่แสดงกรอบหลังตัด
  (แท็บตัดและหมุนแสดงทั้งภาพ จึงไม่ใส่)
- **หลอดดูดสี**: คลิกจุดที่ควรเป็นสีขาว/เทาบนภาพ → แก้สมการของสมดุลแสงขาวของเรา (คูณในแสงเชิงเส้น) จากสีเฉลี่ย 5×5 พิกเซลของภาพก่อนปรับ → ตั้งอุณหภูมิสีและโทนสี
- **ฮิสโตแกรม** RGB ของภาพหลังแต่งบนสุดของแท็บแสงและสี (นับทุก 4 พิกเซลจากตัวอย่างที่วาด)
- **นำเข้าจาก Lightroom ได้เพิ่ม:** Color Grading (Lightroom 10+ ใช้ชื่อเดิมของ Split Toning สำหรับสีของเงา/ส่วนสว่างและ Balance) และ Vignette หลังตัด
  — สองอย่างนี้ไม่อยู่ในรายการ "นำเข้าไม่ได้" แล้ว · สูตรเป็นของเรา ผลจึงใกล้เคียง ไม่เท่ากัน
- **ตัวอย่างสดยังตรงกับไฟล์ทุกพิกเซล** (ค่าอ้างอิงชุด `sample_pro` เทสต์ทั้ง Rust และ TS รวม Vignette ที่ขึ้นกับตำแหน่ง) · ไม่ต้องเปลี่ยน schema
  (ช่องใหม่ของ `Adjust` อ่านค่าเดิมได้ด้วย `serde(default)`) · คัดลอก/วาง: Levels และ Vignette อยู่ในส่วน "แสง" Color Grading อยู่ในส่วน "สี"
- **ยังไม่ทำ:** Texture/Clarity/Dehaze/Sharpening/ลดนอยส์ (ต้องใช้ตัวกรองตามพื้นที่ — ตัวอย่างสดให้ผลตรงกับไฟล์ยาก), Mask/แปรงเฉพาะจุด, Profile ของ Adobe

## 22. ผู้ช่วย AI: ใช้ AI ที่ผู้ใช้สมัครไว้ และให้ AI ใช้เครื่องมือของแอปแทนได้ (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ "เชื่อมต่อกับ AI ที่ subscription อยู่ได้ เช่น Claude ChatGPT และ Gemini คล้าย PuriCat ... ให้ AI ใช้เครื่องมือในแอปนี้แทนเราได้ทั้งหมด")

- **ใช้ CLI ที่ผู้ใช้ติดตั้งและล็อกอินไว้ ไม่มี API key ในแอป** (แนวทางเดียวกับ PuriCat `AI_INTEGRATION.md`): Claude Code (`claude`), Codex ของ ChatGPT
  (`codex`), Gemini CLI (`gemini`) · แอปไม่ขอ ไม่อ่าน ไม่เก็บรหัสผ่าน/token · ตรวจสถานะด้วย `claude auth status --json` / `codex login status`
  (Gemini ไม่มีคำสั่งบอกสถานะ — รู้เมื่อเริ่มคุย) · **Codex มักมีหลายตัว เลือกตัวที่รุ่นใหม่ที่สุด** รวมตัวที่มากับแอป ChatGPT บน Mac:
  ตัวที่ติดตั้งผ่าน npm (0.133) ถูกบริการปฏิเสธทุกรุ่นโมเดล ส่วนตัวในแอป ChatGPT (0.171) ใช้ได้
- **หนึ่งรอบ = หนึ่ง process ของ CLI** ใน thread เบื้องหลัง ส่งบทสนทนาทั้งหมดทาง stdin ทุกรอบ (CLI ไม่เก็บ session) · UI ดึงเหตุการณ์ด้วย `ai_events`
  แบบ polling (ใช้ได้ทั้งแอปจริงและ dev bridge โดยไม่ต้องมีช่องทาง event แยก) · หยุดได้ · หมดเวลา 15 นาที · ฆ่าทั้ง process group
- **เครื่องมือมาทาง MCP ที่แอปเปิดเฉพาะรอบนั้น** บน `127.0.0.1` port สุ่ม + token สุ่ม (ต่างจาก PuriCat ที่ใช้ Unix socket — TCP ใช้บน Windows ได้ด้วย)
  CLI สั่งรันตัวแอปเองในโหมด `--mcp-bridge <port>` (token ส่งทาง env `PURI_MCP_TOKEN` ไม่อยู่ใน argument ที่ process อื่นอ่านได้)
  · เครื่องมือ: ค้นรูป รายการกิจกรรม/บุคคล ข้อมูลรูป **เปิดดูรูป (ส่ง JPEG ย่อให้ AI เห็น)** แต่งรูปเดียว/หลายรูป (รวมค่าเข้ากับของเดิม) ย้อนเป็นต้นฉบับ
  preset (ดู/ใช้/บันทึก) และแสดงรูปในแชต · **ไม่มี**เครื่องมือลบ ย้าย ย่อไฟล์ หรือส่งออก
- **ให้แก้ได้ทันทีโดยไม่ต้องอนุมัติทีละครั้ง** เพราะการแต่งไม่แตะไฟล์และย้อนได้: ทุกการแก้ของรอบจำค่าเดิมไว้ ปุ่ม "ย้อนการแก้" คืนทุกรูปของรอบนั้นในครั้งเดียว
  (จำในหน่วยความจำจนปิดแอป — ยังไม่บันทึกประวัติลงคลัง)
- **CLI แต่ละตัวได้เฉพาะเครื่องมือของแอป:** Claude `--tools ""` (ไม่มีเครื่องมือในตัวเลย) + `--strict-mcp-config` + `--allowedTools mcp__puriphoto`
  + `--setting-sources ""` · Codex `--sandbox read-only` + `--ignore-user-config` + อนุมัติเครื่องมือของแอปล่วงหน้า
  (`mcp_servers.puriphoto.default_tools_approval_mode="approve"` — รอบแรกไม่ได้ตั้ง Codex ขออนุมัติตอนจะแต่งรูปแล้วถูกปฏิเสธเพราะ exec ไม่มีใครตอบ)
  · Gemini ใช้ `.gemini/settings.json` ในโฟลเดอร์ทำงาน (`trust` เฉพาะ server ของแอป) · CLI ทุกตัวรันในโฟลเดอร์ว่างของแอป
- **สิ่งที่ออกจากเครื่อง:** ข้อความที่คุย บริบท (รูปที่เปิดอยู่) ผลของเครื่องมือ และ**ภาพย่อของรูปที่ AI เปิดดู** ไปยังผู้ให้บริการภายใต้บัญชีของผู้ใช้
  — บอกไว้ในแผงผู้ช่วย และแก้ข้อความ "ข้อมูลอยู่ในเครื่อง" ที่เมนูซ้ายให้ตรงความจริง · ปิดเครื่องมือได้ (AI ตอบอย่างเดียว ไม่เห็นคลัง)
- **หน้าจอ:** แผงด้านขวาเปิดจากเมนูซ้าย "ผู้ช่วย AI" อยู่ข้างตัวดูภาพได้ (เห็นรูปเปลี่ยนตามที่ AI แต่ง) · เลือก Claude / ChatGPT / Gemini · ขั้นที่ AI ใช้เครื่องมือ
  เปิดดูผลแต่ละขั้นได้ · รูปที่ AI แสดงเป็นภาพย่อกดเปิดได้ · คำตอบแสดง Markdown แบบปลอดภัย (ตัวอ่านของ PuriCat — ไม่แทรก HTML) · บทสนทนาไม่บันทึกลงดิสก์
- **ภาษาของ AI:** ตอบภาษาผู้ใช้ แทนตัวว่า "ผม" ลงท้าย "ครับ" (ครั้งแรกที่ลองไม่ได้กำหนด รอบหนึ่งตอบ "ดิฉัน/ค่ะ" อีกรอบ "ผม/ครับ")
- **ยังไม่ทำ (ขั้นถัดไปในแผน):** ให้ AI สร้างภาพใหม่จากรูปที่เลือกตาม prompt/template แล้วบันทึกกลับเข้าคลัง (Codex ของ ChatGPT สร้างภาพได้ — ยืนยันแล้ว
  ด้วยภาพสังเคราะห์ ไฟล์อยู่ที่ `~/.codex/generated_images/<thread>/`), เลือกรุ่นของ AI, บันทึกประวัติการคุย

## 23. ให้ AI สร้างภาพใหม่จากรูปที่เลือก แล้วบันทึกกลับเข้าคลังอย่างเป็นระบบ (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ "ให้เราเลือกรูป ให้ AI นำออกไป Gen เป็นสไตล์ที่ต้องการตาม prompt ... มี prompt ที่เป็น template ... บันทึกกลับมาเก็บไว้ในคลังของเราได้เลย อย่างเป็นระบบ")

- **ใช้ Codex ของ ChatGPT** (บัญชีที่ผู้ใช้สมัคร) เพราะมีเครื่องมือสร้างภาพในตัว — Claude สร้างภาพไม่ได้ · Gemini CLI ต้องใช้ API key แยก (ไม่ใช้)
  · ยืนยันกับของจริงแล้ว: ภาพสังเคราะห์ → ภาพวาดสีน้ำมัน/สีน้ำ 1536×1024 ราว 30 วินาทีต่อภาพ ไฟล์อยู่ที่ `~/.codex/generated_images/<รหัสรอบ>/`
- **เข้าได้สองทาง:** ปุ่ม "สร้างภาพด้วย AI" ในแถบเลือกรูป และเมนู ⋮ ของตัวดูภาพ · ครั้งละไม่เกิน 10 รูป (รูปละหนึ่งภาพ ทำทีละรูป) · แม่แบบ 8 แบบ
  (สีน้ำ สีน้ำมัน การ์ตูน ลายเส้นดินสอ ขาวดำคลาสสิก ตุ๊กตาดินปั้น 3 มิติ โปสเตอร์งานบุญ ภาพบุคคลแสงสตูดิโอ) ที่แก้คำสั่งต่อได้ หรือพิมพ์เองทั้งหมด
  · ความคืบหน้าแสดงในแผงผู้ช่วย AI (ปิดหน้าต่างแล้วทำต่อได้)
- **ส่งอะไรออกไป:** สำเนาย่อด้านยาว 2,048 px ของรูปตามที่แต่งไว้ (ไม่ใช่ไฟล์ต้นฉบับเต็ม) + คำสั่ง — บอกไว้ในหน้าต่าง
- **เก็บอย่างเป็นระบบ:** JPEG (คุณภาพ 92) ที่ `รูปภาพ/Puri Photo Search/ภาพจาก AI/<ชื่อกิจกรรมต้นทาง>/<ชื่อไฟล์ต้นทาง>-ai-<n>.jpg`
  — หนึ่งโฟลเดอร์ต่อกิจกรรมต้นทาง เข้าคลังเป็นกิจกรรม "<ชื่อกิจกรรม> · ภาพจาก AI" (วันกิจกรรมเท่าต้นทาง วิเคราะห์ใบหน้าด้วย) · ครั้งต่อไปสแกนเพิ่มในกิจกรรมเดิม
  · เขียนไฟล์ชั่วคราวแล้วเปลี่ยนชื่อ (ตัวสแกนไม่เห็นไฟล์ครึ่ง ๆ) · ไม่เขียนลงโฟลเดอร์รูปของผู้ใช้
- **ที่มาผูกกับไฟล์ด้วย SHA-256** (ตาราง `ai_images`, schema v8): รูปต้นทาง ชื่อไฟล์ต้นทาง คำสั่ง แม่แบบ AI ที่ใช้ เวลา — ย้ายโฟลเดอร์แล้วยังรู้ที่มา ·
  ตัวดูภาพแสดง "ภาพที่ AI สร้าง" พร้อมลิงก์เปิดรูปต้นทาง (ถ้ารูปต้นทางไม่อยู่ในคลังแล้ว บอกตามจริง) · ภาพสองภาพที่เหมือนกันทุก byte ใช้ที่มาของภาพหลังสุด
- **ยังไม่ทำ:** เลือกโฟลเดอร์ปลายทางเอง, ใส่ EXIF/วันถ่ายให้ภาพที่สร้าง (ตอนนี้ "ไม่ทราบวันถ่าย"), สร้างหลายภาพจากรูปเดียว, สร้างจากหลายรูปรวมเป็นภาพเดียว,
  ให้ AI ในแชตสั่งสร้างภาพเอง (ตอนนี้กดจากหน้าต่าง)

## 24. แต่งตามภาพตัวอย่าง (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ "อยากให้เลือกสไตล์ภาพที่ต้องการจากภาพ ref แล้วให้ AI แต่งภาพอื่นๆที่เลือกไว้ ตามนั้นได้")

- **เข้าได้สองทาง:** แถบเลือกรูป "ใช้ AI ▾" → "แต่งตามภาพตัวอย่าง…" (คลิกรูปหนึ่งในที่เลือกเป็นภาพตัวอย่าง หรือเลือกไฟล์ JPEG/PNG จากเครื่อง)
  และเมนู ⋮ ของตัวดูภาพ "ใช้เป็นภาพตัวอย่างในผู้ช่วย AI" · ภาพตัวอย่างติดอยู่กับการคุย (แถบเหนือช่องพิมพ์) จนกด ✕ หรือเริ่มคุยใหม่
- **สองแบบ:** (1) **แต่งให้ดูเหมือน** — AI ที่เลือกในแผงใช้เครื่องมือแต่งภาพของแอป (ไม่แตะไฟล์ ย้อนได้ทั้งรอบ ครั้งละไม่เกิน 20 รูป) ·
  (2) **สร้างภาพใหม่ตามสไตล์** — ChatGPT ได้สองภาพ (ภาพตัวอย่างก่อน แล้วรูปที่จะสร้าง) ครั้งละไม่เกิน 10 รูป ที่มาบันทึกแม่แบบเป็น "ตามภาพตัวอย่าง “…”" (ข้อ 23)
- **เครื่องมือของ AI สองตัวขึ้นเฉพาะรอบที่มีภาพตัวอย่าง:** `view_reference` (เห็นภาพ + ตัวเลขของลุค) และ `compare_to_reference` (ค่าที่เสนอสำหรับรูปหนึ่ง)
  · AI ใช้ค่าที่เสนอเป็นจุดเริ่ม ดูผลด้วยตาแล้วปรับเอง (เจอจริง: AI ลด tint ที่เสนอ −26 เหลือ −12 เพราะผิวออกเขียว)
- **วัดลุคเป็นตัวเลขใน CIE Lab บนภาพย่อ 256 px** (`assistant/look.rs`): ความสว่าง L* ที่เปอร์เซ็นไทล์ 2/25/50/75/98 · ความอิ่มสี ·
  **โทนสีวัดจากส่วนที่เกือบเป็นสีเทาเท่านั้น** (มัธยฐาน) ช่วงกลาง = สมดุลแสงขาว เงา/ส่วนสว่าง = split toning — สีของสิ่งของ (จีวรส้ม ต้นไม้) ไม่ใช่โทนของภาพ
  ถ้าเฉลี่ยทั้งภาพจะไปแก้สมดุลแสงขาวเพื่อลบสีของเนื้อหา (เจอจริงในเทสต์รอบแรก)
- **ภาพตัวอย่างที่แต่งในแอป → คัดลอกค่าแสงสีทั้งชุด** แล้วหาเฉพาะค่าแสง (ความสว่างกลาง) และสมดุลแสงขาว (ส่วนสีเทาจริง) ให้แต่ละรูป แทนค่าเดิมของรูปทั้งหมด
  แบบใช้ preset (ข้อ 20) — คอนทราสต์และความอิ่มสีที่วัดจากภาพขึ้นกับเนื้อหามาก: ภาพตัวอย่างลดความอิ่มสี −25 แต่รูปเป้าหมายสีจืดกว่า การวัดจึงเสนอ **+30**
  สวนทางกับสไตล์ (เจอจริงกับ Claude) · **ภาพตัวอย่างอื่น** (ไฟล์ หรือรูปที่ไม่ได้แต่ง) ค้นหาค่าแสง คอนทราสต์ อุณหภูมิสี/tint ความอิ่มสี และ Color Grading
  ของเงา/ส่วนสว่าง ด้วยสูตรแต่งภาพตัวจริง (`adjust::apply`) ในช่วงจำกัด (±1.5 EV, ±40, ความอิ่มสี ±30, grading ≤ 60) และบอก AI ว่าคอนทราสต์/ความอิ่มสีขึ้นกับเนื้อหา
- **ค่าที่เสนอเป็นค่าจริงที่คิดจากรูปก่อนปรับค่าเหล่านี้ — ถามซ้ำได้คำตอบเดิม:** รุ่นแรกเสนอ "ส่วนเพิ่ม" บนภาพที่แต่งแล้ว เมื่อเนื้อหาทำให้วัดไม่ถึงภาพตัวอย่าง
  รอบสองจึงสะสมแรงขึ้นเรื่อย ๆ (เจอจริง: tint −65 ความอิ่มสี −55 ในรูปที่มีผนังเหลืองและดอกไม้ชมพู) · ค่าอื่นของรูป (HSL เส้นโค้ง ฯลฯ) คงไว้และคิดรวม ·
  บอกระยะห่างจากภาพตัวอย่าง "ตอนนี้" กับ "เมื่อใช้ค่าที่เสนอ" ให้ AI ใช้ตรวจ ไม่ใช่ขยับต่อ
- **สีเทาจริงของรูปที่จะแต่ง: chroma < 10 และ < 0.12 × L\*** (ภาพตัวอย่างใช้ < 18 เพราะส่วนสีเทาของภาพที่ทำโทนแล้วมีสีได้) — สีอ่อนของสิ่งของ (ผนังเหลืองอ่อน
  ดอกไม้ชมพู ผิว) อยู่เหนือเกณฑ์ · ใช้สัดส่วนต่อ L\* ด้วยเพราะส่วนที่อยู่ในเงาของสีอ่อน chroma ลดตามความสว่าง (ผนังเหลืองอ่อนที่ L\* 52 มี chroma ราว 9.8) ·
  ส่วนสีเทาเลือกครั้งเดียวก่อนค้นหาแล้ววัดส่วนเดิมทุกครั้ง ผลจึงเปลี่ยนตามค่าที่ลองอย่างราบรื่น · ไม่พอ 3% ของภาพ → ไม่แตะสมดุลแสงขาว และบอก AI ให้ดูด้วยตา
- **ภาษา:** AI เขียนหมายเหตุระหว่างใช้เครื่องมือเป็นภาษาอังกฤษ ("Both look good now…") แม้คำสั่งตั้งต้นบอกให้ใช้ภาษาผู้ใช้ — ย้ำทั้งในคำสั่งตั้งต้นและท้ายข้อความทุกรอบ
  (คำตอบรวมข้อความทุกช่วงของรอบ หมายเหตุจึงขึ้นในคำตอบด้วย)
- **ส่งอะไรออกไป:** แบบแต่ง = ภาพตัวอย่างและรูปที่ AI เปิดดู (ย่อแล้ว) · แบบสร้าง = ภาพตัวอย่างและแต่ละรูป ด้านยาว 2,048 px — บอกไว้ในหน้าต่าง
- **ยังไม่ทำ:** ภาพตัวอย่างหลายภาพ, เทียบเฉพาะบริเวณ (เช่น สีผิว), ภาพตัวอย่างที่เป็น RAW/HEIC, แสดงภาพย่อของไฟล์ภาพตัวอย่างในหน้าต่าง (UI อ่านไฟล์ข้างนอกไม่ได้ — แสดงชื่อไฟล์)

## 25. ไฟล์ RAW จากกล้อง (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ขอ "ถ้าโปรแกรมเรารองรับไฟล์ RAW ได้ด้วยจะดีมาก เพราะการแต่งภาพด้วยไฟล์ RAW จะทำได้ดีที่สุด")

- **ตัวถอดรหัส: crate `rawler` 0.8** (pure Rust ของโครงการ dnglab) — ลองกับไฟล์จริงของเจ้าของผลิตภัณฑ์แล้วเปิดได้ทั้ง Sony ILCE-7CM2
  (ARW แบบ lossless compressed ทั้งชนิด Bayer และชนิด LinearRaw ที่กล้องรวมพิกเซลมาแล้ว — สองชนิดปนกันในโฟลเดอร์เดียว) และ Panasonic DC-S5 (RW2)
  · ไม่ใช้ ImageIO ของ macOS เพราะต้องการผลเท่ากันบน Windows และทดสอบได้ · ไม่ใช้ LibRaw เพราะเป็น C++ ต้อง build ทั้งสองระบบ ·
  **สัญญาอนุญาต LGPL-2.1:** ลิงก์แบบ static ใน Rust ผู้ใช้ต้องสร้างแอปใหม่กับ rawler ที่แก้เองได้ — repo นี้เปิด source อยู่แล้ว
  (ถ้าวันหนึ่งจะปิด source ต้องเปลี่ยนตัวถอดรหัส) · ตัวติดตั้งโตขึ้นจากโค้ดของ rawler
- **ล้างภาพเอง (`raw.rs`):** rawler ถอดรหัส ลบระดับดำ/หารระดับขาว demosaic (PPG) และตัดขอบตามกล้อง · แอปทำสมดุลแสงขาวของกล้อง → เมทริกซ์สี →
  sRGB เชิงเส้น · **ไม่ตัดค่าเกิน 1** (เก็บถึง 2 = 1 stop — สีสดในที่สว่าง เช่น จีวรกลางแดด มีช่องแดงเกิน 1) · ช่องเขียวเต็มเซนเซอร์ → ค่อย ๆ เป็นสีกลาง
  (ไม่งั้นส่วนสว่างออกชมพู) — ขั้นสีของ rawler เองเฉลี่ยทุกพิกเซลที่เกิน 1 เข้าหาสีเทา ทำให้สีสดในที่สว่างซีด จึงไม่ใช้
- **โทนตั้งต้นใกล้ภาพที่กล้องสร้าง:** เส้นโค้งโทน (log2 ของแสง → ค่าที่แสดง) วัดจาก JPEG ที่กล้องฝังไว้ในไฟล์ RAW จริง 79 ไฟล์ (Sony 30 + Lumix 49)
  ใช้ค่ากลางของสองกล้อง (Sony สว่างกว่าในเงา น่าจะเปิด DRO) · ใส่ต่อช่องสี + เพิ่มความอิ่มสี 1.1 เท่าในแสงเชิงเส้น (เส้นโค้งอย่างเดียวจืดกว่ากล้อง 6%
  — 1.1 เท่าวัดได้ 0.99 เท่าของกล้อง) · ดูภาพเทียบกันแล้วใกล้ภาพของกล้องทั้งสองยี่ห้อ ([TEST_REPORT.md](TEST_REPORT.md) หมวด RAW) · เปิด RAW มาจึงไม่จืดกว่า JPEG
- **แต่ง RAW แบบโปรแกรมแต่ง RAW:** ค่าแสงและสมดุลแสงขาวทำในแสงของฉาก **ก่อน**เส้นโค้งโทน — เพิ่มค่าแสงแล้วส่วนสว่างม้วนเข้าหาขาวแทนการตัด
  (ภาพทั่วไปค่าแสง +1 ทำให้ทุกอย่างที่สว่างกว่าราว 190/255 ขาวสุด) · ขั้นที่เหลือ (เงา ส่วนสว่าง คอนทราสต์ เส้นโค้ง HSL Color Grading ฯลฯ) สูตรเดิม ·
  **ภาพย่อ ตัวดูภาพ และไฟล์ที่ส่งออกคำนวณจากข้อมูลเต็มของ RAW แบบทศนิยม** (ตาราง 4096 ค่าต่อช่อง เรียงตามรากที่สองของแสง) ไม่ผ่าน 8 บิต จึงไล่น้ำหนักเนียนกว่า
  แต่งจาก JPEG · ย่อภาพในแสงเชิงเส้น
- **ตัวอย่างสดในหน้าแต่งภาพ:** WebView ทำงานกับภาพ 8 บิตเท่านั้น → ภาพต้นทางของรูป RAW คือโทนตั้งต้น 8 บิต (asset `original`) แล้ว `adjust.ts` ถอดกลับเป็น
  แสงเชิงเส้นด้วยเส้นโค้งย้อนกลับ ก่อนคิดค่าแสง/สมดุลแสงขาวแล้วทำโทนซ้ำ — ไม่ปรับอะไร = ภาพเดิมทุกระดับ (ไม่มีขั้นบันไดเพิ่ม) · หลอดดูดสีและปรับอัตโนมัติถอดกลับแบบเดียวกัน ·
  ค่าอ้างอิงชุดเดียวกันใน Rust และ TS · **ข้อจำกัด:** ดึงส่วนสว่างลงมาก ๆ ตัวอย่างสดอาจเห็นเป็นขั้น ภาพที่บันทึกแล้วเนียนกว่า (คำนวณจากข้อมูลเต็ม)
- **ภาพย่อ ตัวดูภาพ ตัววิเคราะห์ใบหน้า และผู้ช่วย AI ใช้โทนตั้งต้นเดียวกัน** (ไม่ใช้ JPEG ที่กล้องฝังไว้ — สีจะไม่ตรงกับหน้าแต่งภาพ) · ล้างแบบครึ่งขนาด
  (รวมพิกเซล 2×2) เมื่อขอภาพไม่เกินครึ่งหนึ่งของภาพเต็ม: 1200 px ราว 0.12 วินาทีต่อรูป (release) · "ต้นฉบับ" ของรูป RAW สำหรับ UI เป็น JPEG 2560 px เก็บใน cache ตาม revision
- **ส่งออก:** RAW เป็น JPEG เสมอ (ชื่อ .jpg — ผู้รับเปิดไฟล์ RAW ไม่ได้) ทั้งที่แต่งและไม่แต่ง · EXIF สร้างใหม่จากไฟล์ RAW: กล้อง เลนส์ วันถ่าย ความเร็วชัตเตอร์
  รูรับแสง ISO ทางยาวโฟกัส Orientation = 1 (ภาพตั้งตรงแล้ว) · ไม่ฝังโปรไฟล์สี (sRGB) · **ย่อไฟล์ต้นฉบับไม่รวม RAW** (เฉพาะ JPEG เหมือนเดิม)
- **นำเข้าเมื่อเลือกเท่านั้น (schema v9 `event_source_bindings.include_raw`):** โฟลเดอร์งานของเจ้าของผลิตภัณฑ์มี JPEG ที่ export จาก Lightroom อยู่ชั้นบน
  และ RAW ทุกช็อต (รวมช็อตที่คัดทิ้ง) ในโฟลเดอร์ย่อย `sony_raw/` `lumix_raw/` — นำเข้า RAW เองอัตโนมัติจะได้รูปซ้ำและรูปที่คัดทิ้ง → หน้าเพิ่มโฟลเดอร์นับ RAW แยก
  และมีสวิตช์ "รวมไฟล์ RAW" **เปิดไว้ก่อนเฉพาะโฟลเดอร์ที่มีแต่ RAW** · จำไว้กับกิจกรรม ตรวจรูปใหม่ครั้งต่อไปใช้ค่าเดิม · **กิจกรรมที่มีอยู่ก่อนเป็น 0** —
  อัปเดตแอปแล้วตรวจรูปใหม่ไม่ได้ RAW เพิ่มเอง · อยากได้ RAW ในกิจกรรมเดิม: เพิ่มโฟลเดอร์เดิมอีกครั้งแล้วเปิดสวิตช์ (ไม่มีทางปิดกลับ — ไม่ลบรูปที่นำเข้าแล้ว)
- **ยังไม่ทำ:** ลดนอยส์ ความคม แก้เลนส์, โปรไฟล์แยกตามรุ่นกล้อง,
  เลือกไฟล์ RAW นอกคลังเป็นภาพตัวอย่างของผู้ช่วย AI (รูป RAW ในคลังใช้ได้), กล้องที่ rawler ยังไม่รู้จัก (แจ้งเป็นรายไฟล์ว่าเปิดไม่ได้)
  · จับคู่ RAW กับ JPEG ทำแล้วในข้อ 26 (สวิตช์ "รวมไฟล์ RAW" เหลือผลเฉพาะ RAW ที่ไม่มีคู่)

## 26. RAW + JPEG ของช็อตเดียวกันเป็นรูปเดียว แบบ Lightroom (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์เลือก "Paired เหมือน Lightroom ก็ดีนะ")

- **รูปเดียว ไฟล์หลักคือ JPEG:** ภาพที่แสดง ใบหน้า ชื่อ วันถ่าย ขนาด เป็นของ JPEG เหมือนเดิม (JPEG ที่ส่งออกจาก Lightroom คือผลงานที่แต่งเสร็จแล้ว
  และใบหน้าตรวจบน JPEG) · ไฟล์ RAW เป็น "คู่" ของรูป (schema v10 `photo_raw_pairs`) ไม่เป็นรูปแยก · ไฟล์ทั้งสองไม่ถูกแตะ · ป้าย RAW+JPEG บนภาพย่อ
- **จับคู่เมื่อ:** (ก) XMP ของ JPEG บอกว่าส่งออกจากไฟล์ RAW ชื่อนั้น (`crs:RawFileName`) อยู่โฟลเดอร์ไหนก็ได้ในกิจกรรมเดียวกัน — ตรงกับโครงของเจ้าของผลิตภัณฑ์
  (JPEG ชั้นบน RAW ใน `sony_raw/` `lumix_raw/`) · (ข) ชื่อเดียวกันในโฟลเดอร์เดียวกัน (กล้องบันทึก RAW+JPEG) · อ่าน XMP เฉพาะ JPEG ที่มี RAW ชื่อเดียวกัน
  ในกิจกรรม (ไม่อ่านหัวไฟล์ทุกรูปของคลังใหญ่) — **JPEG ที่เปลี่ยนชื่อตอนส่งออก หรือ Virtual Copy ที่ชื่อมี -2 ต่อท้าย จึงไม่จับคู่** · RAW ไฟล์เดียวเป็นคู่ของหลาย JPEG ได้ ·
  RAW ที่เป็นรูปในคลังอยู่แล้ว (นำเข้าแยกไว้ก่อน) คงเป็นรูปเดิม ไม่ย้ายใบหน้า/ชื่อ/การแต่งไปไหน · ไฟล์ RAW หายไปภายหลัง = คู่ "ไม่พร้อม" ไม่ลบ
- **สวิตช์ "รวมไฟล์ RAW" มีผลเฉพาะ RAW ที่ไม่มีคู่** (ช็อตที่คัดทิ้ง ไม่ได้ส่งออก) · หน้าเพิ่มโฟลเดอร์บอกจำนวน RAW ที่เป็นคู่แยกจาก RAW ที่ไม่มีคู่ ·
  โฟลเดอร์ย่อยที่มีแต่ RAW คู่ของ JPEG ข้างนอกไม่นับเป็นงานแยกตอนเสนอ "หลายงาน" · กิจกรรมเดิมได้คู่เมื่อตรวจรูปใหม่ (ไม่ขึ้นกับสวิตช์)
- **แต่งรูปคู่ = แต่งจาก RAW:** ล้าง RAW แล้ววางลงกรอบเดียวกับ JPEG ก่อนตัด/หมุนตามที่แต่ง — กรอบจาก `crs:CropTop/Left/Bottom/Right/CropAngle`
  (สัดส่วนบนภาพตามแนวที่เก็บในไฟล์ RAW ก่อนหมุนตาม Orientation · มุมบนซ้ายและล่างขวาของกรอบที่เอียงแล้ว) ตรวจกับไฟล์จริง 135 คู่: ขนาดที่คิดได้ตรงกับ JPEG
  ทุกไฟล์ (ต่างไม่ถึง 0.02%) · เทียบตำแหน่งภาพจริง: Sony ตรงกันทั้งภาพ · Lumix คลาดราว 0.3% ที่ขอบภาพ เพราะการแก้เลนส์ของ Lightroom (ทำตามไม่ได้) ·
  สัดส่วนไม่ตรง (หมุนภาพใน Lightroom / กล้องตั้งสัดส่วน JPEG อื่น) = แต่งจาก JPEG แทน พร้อมบอกเหตุ
- **ค่าเริ่มต้นจาก Lightroom แล้วปรับให้ภาพเท่ากับ JPEG:** อ่านค่าที่ตัวแต่งภาพของเราทำได้จาก XMP (แสง ความสด HSL เส้นโค้ง Color Grading Vignette — ตัวอ่านเดียวกับ
  preset ข้อ 20) · สมดุลแสงขาวแบบ Kelvin คิดเทียบกับค่าของกล้อง (จุดขาวจากตัวคูณสมดุลแสงขาว + เมทริกซ์สีของกล้อง → Bradford) ไม่ใช่เทียบ 5500 K แบบ preset ·
  สูตรโทนของเรากับของ Adobe ต่างกันและ Mask/Denoise ของ Lightroom ทำตามไม่ได้ จึง**ปรับค่าแสงและสมดุลแสงขาวต่อให้ค่าเฉลี่ย L\* a\* b\* ของภาพจาก RAW เท่ากับของ JPEG**
  (ภาพเดียวกัน กรอบเดียวกัน ไม่นับส่วนที่ขาว/ดำจนหมดรายละเอียด) — RAW ขนาด M ของ Sony ปรับสมดุลแสงขาวมาในข้อมูลแล้ว อ่านแสงของกล้องไม่ได้ ใช้การปรับนี้อย่างเดียว ·
  ไฟล์จริง 10 คู่: ต่างจาก JPEG ไม่เกิน ±1.3 L\* ±1.2 a\* ±2.4 b\* (ก่อนปรับต่าง −4 ถึง −7.5 L\*) · คิดครั้งแรกที่ต้องใช้ (ราว 0.2–0.4 วินาทีต่อรูป release) แล้วเก็บไว้ ·
  JPEG ที่ไม่ใช่ sRGB (มีโปรไฟล์สีอื่น) ไม่ปรับ
- **"ไม่ได้แต่ง" ของรูปคู่ = ค่าเริ่มต้น:** บันทึกค่าเริ่มต้นกลับไป = ลบการแต่ง (แสดง JPEG ตามเดิม ซึ่งมี Mask/Denoise ของ Lightroom ครบ) · กลับเป็นต้นฉบับ = JPEG
  ไม่ใช่ RAW ที่ไม่ได้แต่ง · ปุ่มรีเซ็ตในหน้าแต่งภาพกลับไปที่ค่าเริ่มต้น · วาง/preset/ผู้ช่วย AI ใช้ค่าเริ่มต้นเป็นค่าปัจจุบันของรูปที่ยังไม่แต่ง
- **การแต่งจำว่าทำกับไฟล์ไหน (`EditSettings.fromRaw` แอปตั้งเอง):** การแต่งที่ทำกับ JPEG ก่อนพบคู่ RAW ยังเป็นของ JPEG (ค่าเดิมมีความหมายเท่าเดิม) จนกว่าจะกลับเป็นต้นฉบับ ·
  การแต่งจาก RAW แสดง/ส่งออกจาก RAW เสมอ — ไฟล์ RAW ไม่พร้อม: ตัวดูภาพแสดง JPEG แทน (ไม่ล้ม) และการส่งออกรูปนั้นแจ้งเหตุเป็นรายไฟล์
  (ดีกว่าได้ภาพที่ไม่ได้แต่งโดยไม่รู้ตัว) · ส่งออก: ขนาดเท่ากรอบของ JPEG · EXIF ของ JPEG · ไม่ติดโปรไฟล์สีของ JPEG (ภาพจาก RAW เป็น sRGB)
- **บอกตามจริงว่าทำตามอะไรไม่ได้:** หน้าแต่งภาพแสดงส่วนที่แต่งใน Lightroom แต่แอปทำตามไม่ได้ (Texture, Clarity, Sharpening, แก้เลนส์, Denoise (AI), Mask n อัน) ·
  ตัวนำเข้า preset .xmp บอกแก้เลนส์และ Denoise/Enhance ด้วย
- **ยังไม่ทำ:** แก้เลนส์ (ความโค้งและขอบมืด) จากข้อมูลในไฟล์ RAW, Texture/Clarity/Mask (ขั้นต่อไปที่เจ้าของผลิตภัณฑ์อนุมัติแล้ว), JPEG ที่เปลี่ยนชื่อตอนส่งออก

## 27. Texture, Clarity, Dehaze (21 พ.ย. 2569 — เจ้าของผลิตภัณฑ์ถามว่าเครื่องมือของแอปละเอียดพอให้ AI แต่งตาม brief อย่าง "หน้าขาวใส" ได้ไหม แล้วอนุมัติแผน: ขั้นที่ 1 Texture/Clarity/Dehaze → ขั้นที่ 2 Mask แบบไม่ใช้โมเดลเพิ่ม (ใบหน้า/ผิวก่อน) → ปุ่ม "ให้ AI ปรับ")

- **ทำไม:** เครื่องมือเดิมปรับต่อพิกเซลทั้งหมด จึงทำผิวเนียนนุ่ม (Texture/Clarity ลบ) ไม่ได้ · เจ้าของผลิตภัณฑ์ใช้ Texture −10 และ Clarity −7 ถึง −25
  แทบทุกรูปใน Lightroom (ตรวจ XMP 135 ไฟล์) — ตอนนี้ preset และรูปคู่ RAW ทำตามค่าเหล่านี้ได้ (ออกจากรายการ "ทำตามไม่ได้")
- **วิธี (`local.rs` / `local.ts` สูตรเดียวกัน):** ทำหลังขั้นต่อพิกเซลทั้งหมด บนภาพผล 8 บิต · รัศมีเป็นสัดส่วนของด้านยาวของกรอบก่อนตัด (ตัวอย่างสดบนจอ
  ภาพย่อ และไฟล์เต็มขนาดได้ผลแบบเดียวกัน ตัดภาพแล้วผลไม่เปลี่ยน — ข้อ 29) · **Texture / Clarity:** ความสว่าง + k·(ความสว่าง − ฐาน) โดยฐานมาจาก guided filter (เบลอแบบรักษาขอบ —
  ขอบชัดอย่างตา ผม ขอบวัตถุ ไม่เบลอและไม่เกิดรัศมี) · Texture รัศมี 0.35% ของด้านยาว · Clarity รัศมี 1.5% คูณน้ำหนักช่วงกลาง (0 ที่ดำ/ขาวสุด) ·
  **Dehaze:** dark channel prior แบบย่อ — สีของหมอกจาก 1% ของบล็อกที่ dark channel สูงสุด ความโปร่งคิดทีละบล็อก (1% ของด้านยาว) แล้ว guided filter
  ทำตามขอบ · ค่าลบ = เข้าหาสีของหมอก · guided filter คิดที่ความละเอียดต่ำแล้วขยายสัมประสิทธิ์กลับ (fast guided filter) หน่วยความจำเพิ่มแค่ความสว่างหนึ่งชุด
- **ตัวอย่างสดกับภาพที่บันทึกตรงกัน:** ค่าอ้างอิงร่วม `LOCAL_EXPECTED` (Rust เท่ากันทุกค่า · TS ต่างไม่เกิน 1 ระดับจากการปัดทศนิยม)
- **ความเร็ว:** ภาพ 24 MP (release) Texture 277 ms · Clarity 274 ms · Dehaze 325 ms · ทั้งสามรวม 0.77 วินาที · ตัวอย่างสดในเบราว์เซอร์ (1100×760)
  29–85 ms ต่อแถบ รวมสามแถบ 124 ms
- **ค่าที่บันทึกก่อนรุ่นนี้ไม่มีช่องเหล่านี้ = 0** (ตัวอย่างสดเคยได้ NaN จนภาพดำทั้งภาพ — แก้แล้วและมีเทสต์) · วาง "แสง" ระหว่างรูปรวมสามค่านี้ ·
  ผู้ช่วย AI รู้จักทั้งสามค่า · ค่าเริ่มต้นของรูปคู่ RAW คิดใหม่ (รุ่นของวิธีคิด 3) และอ่านค่าของ Lightroom ใหม่จาก XMP ของ JPEG
- **ยังไม่ทำ:** ลดนอยส์แบบจริงจัง (Texture ลบช่วยลดนอยส์ได้บ้าง แต่ไม่เท่า Denoise ของ Lightroom), ความคม (Sharpening), ปรับเฉพาะส่วน (Mask — ขั้นที่ 2)

## 28. ปรับเฉพาะส่วน (Mask) เริ่มจากใบหน้าและผิว (21 พ.ย. 2569 — ขั้นที่ 2 ของแผนในข้อ 27 ที่เจ้าของผลิตภัณฑ์อนุมัติ: Mask แบบไม่ใช้โมเดลเพิ่ม ใบหน้า/ผิวก่อน)

- **ทำไม:** เจ้าของผลิตภัณฑ์ใช้ Mask ใน Lightroom จริงแทบทุกรูป (Subject/Clothes/Hair/Ground — ข้อ 26) และงานรูปบุคคลต้องการ "หน้าสว่าง ผิวเนียน
  หน้าขาวใส" โดยจีวร เสื้อผ้า และฉากหลังไม่เปลี่ยน — ปรับทั้งภาพทำไม่ได้
- **บริเวณใบหน้า:** ใช้กรอบใบหน้าที่แอปมีอยู่แล้ว (ตัววิเคราะห์ใบหน้า + กรอบที่ผู้ใช้วาดเอง) ไม่ต้องดาวน์โหลดโมเดลใหม่ · วงรีนุ่มรอบกรอบ: ครึ่งบนสั้น
  (0.62 เท่าของความสูงกรอบ ไม่ล้นขึ้นไปบนฉากหลังเหนือศีรษะ) ครึ่งล่างยาว (0.85 คลุมคางและคอ) เต็มที่ถึง 0.75 ของรัศมี จางหมดที่ 1.15 ·
  **"เฉพาะผิว"** (เปิดไว้ก่อน) = Cb/Cr ของ YCbCr อยู่ในช่วงสีผิว (จีวรส้มสด เทา ขาว ผมหงอก อยู่นอกช่วง) × ใกล้สีผิวของคนนั้น (Cb/Cr เฉลี่ยของ
  กลางใบหน้า: ห่างไม่เกิน 10 เต็มที่ เกิน 20 ไม่ใช่) — กันฉากหลังสีทอง/ครีมที่บังเอิญอยู่ในช่วงสีผิว ซึ่งเจอในรูปจริง
- **ค่าของบริเวณ:** ค่าแสง คอนทราสต์ ส่วนสว่าง เงา · Texture Clarity Dehaze · อุณหภูมิสี โทนสี ความอิ่ม · ความแรง 0–100% · กลับด้าน ·
  จุดเริ่มสำเร็จรูป "หน้าสว่างขึ้น" "ผิวเนียน" "ผิวขาวใส" · กดค้างเพื่อดูบริเวณเป็นสีแดง (และแสดงชั่วครู่ตอนเพิ่ม) · ไม่เกิน 10 บริเวณต่อรูป
- **ลำดับและพิกัด:** ทำหลังแสงสีของทั้งภาพ (รวม Texture/Clarity/Dehaze) บนภาพผล 8 บิต — ปรับเฉพาะส่วนที่ครอบบริเวณ แล้วผสมกับภาพเดิมตามน้ำหนัก ·
  พิกัดเป็นสัดส่วนบนภาพเดิม (ก่อนตัด/หมุนของการแต่ง) ตัด/หมุนใหม่แล้ว Mask ยังอยู่ที่เดิมบนภาพ · รูปคู่ RAW ใช้กรอบของ JPEG (ภาพจาก RAW อยู่ในกรอบเดียวกัน)
- **ตัวอย่างสดกับภาพที่บันทึกตรงกัน:** `masks.rs` ↔ `masks.ts` สูตรเดียวกัน ค่าอ้างอิงร่วม `MASK_EXPECTED` (TS ต่างไม่เกิน 1 ระดับ) · รูปจริงเทียบตัวอย่างสด
  กับภาพที่บันทึก ค่าเฉลี่ยในบริเวณหน้า ฉากหลัง และจีวร ต่างไม่เกิน 2 ระดับ
- **วางการแต่งให้หลายรูป:** ตัวเลือกใหม่ "ปรับเฉพาะส่วน" — บริเวณใบหน้าใช้ใบหน้าที่แอปพบ **ในแต่ละรูปเอง** (แบบ Sync ของ Lightroom ที่หาคนใหม่ทุกรูป)
  ไม่ใช่ตำแหน่งใบหน้าของรูปต้นทาง · ติ๊กไว้ก่อนเมื่อการแต่งที่คัดลอกมี Mask · วางเฉพาะแสง/สี และใช้ preset ไม่แตะ Mask ของรูปปลายทาง · preset ไม่เก็บ Mask
- **ความเร็ว:** 24 MP release 3 หน้า "ผิวขาวใส" 240–320 ms · กลับด้าน (ทั้งภาพ) ~1 วินาที · ตัวอย่างสดในเบราว์เซอร์ 1100×760: 25–33 ms · กลับด้าน 125–140 ms
- **ข้อจำกัด:** ได้แค่ใบหน้าที่มีกรอบ — ผิวแขน/มือยังไม่รวม (แผงบอกไว้) · กรอบที่วาดเองหลวม ๆ (สูงกว่าหน้ามาก) ทำให้วงรีเลยขึ้นไปบนฉากหลังเหนือศีรษะได้
  ถ้าฉากหลังสีใกล้ผิว (เจอกับกรอบที่ผมวาดเองในรูปทดสอบ — กรอบจากตัววิเคราะห์ใบหน้าแน่นพอ ไม่ล้น) · ยังเลือกเฉพาะบางคนในรูปไม่ได้ (ทุกใบหน้าของรูป
  รวมใบหน้าบนโปสเตอร์ที่ตัวตรวจพบ) · ยังไม่มี Mask ไล่ระดับ (Linear/Radial) ช่วงสี/ความสว่าง และแบบใช้ AI แยกคน/ท้องฟ้า (ขั้นที่ 3 — ตัดสินใจภายหลัง) ·
  ผู้ช่วย AI ยังสร้าง Mask เองไม่ได้ (ทำพร้อมปุ่ม "ให้ AI ปรับ") แต่แต่งต่อแล้ว Mask เดิมยังอยู่ · Mask ของ Lightroom ใน preset/XMP ยังนำเข้าไม่ได้ (บอกในรายการทำตามไม่ได้)

  สีเดียว นอยส์ พื้นผิวละเอียด ฉากที่มีใบหน้าตรงกรอบของ Mask) 400 ชุด seed ตายตัว · Rust คิดด้วยขั้นเดียวกับภาพที่บันทึก แล้วเรียก vitest

- **ที่เทสต์จับได้และแก้แล้ว** (ทุกข้อเก็บเป็นเทสต์ตายตัวทั้งสองฝั่ง):
  1. **รูปที่ตัด + Texture/Clarity/Dehaze หรือ Mask:** ตัวอย่างสดคิดรัศมี (และขอบเผื่อของ Mask) จากด้านยาวของกรอบก่อนตัด แต่ไฟล์ที่บันทึกคิดจาก
     ส่วนที่ตัด → ไฟล์ต่างจากที่เห็น · แก้ฝั่ง Rust ให้ใช้กรอบก่อนตัด (`Geometry::frame_long`) แบบ Lightroom: ตัดภาพแล้วผลไม่เปลี่ยน — ภาพที่บันทึก
     ของรูปที่ตัดและใช้ค่าเหล่านี้จึงเปลี่ยนให้ตรงกับที่เห็น (ทั้งสองอย่างยังไม่ได้ออกรุ่น)
  2. **Vignette ในค่าของ Mask** (ส่งมาได้ทาง AI/ค่าที่เก็บไว้ แผงไม่มีแถบนี้): Rust ใส่ตามขนาดบริเวณ ตัวอย่างสดไม่ใส่ → ทั้งสองฝั่งไม่ใช้
     (Vignette เป็นของกรอบทั้งภาพ)
  3. **ทศนิยมของ Texture/Clarity/Dehaze:** Rust คิดด้วย f32 ตัวอย่างสดคิดด้วย f64 แล้วเก็บใน Float32Array → ต่าง 2–6 ระดับเมื่อค่าสุดขอบหรือมี Mask
     · Rust คิดแบบเดียวกัน (f64 แล้วเก็บ f32 ที่จุดเดียวกัน) — ตรงทุกบิต · ความเร็ว 24 MP release (เครื่องมีงานอื่น load ~13 · ดีที่สุดของ 9 ครั้ง สลับกัน):
     Texture 327 → 321 ms · Clarity 306 → 312 ms · Dehaze 377 → 393 ms — ไม่ต่างเกินความแกว่งของการวัด
  4. **การวน hue:** `((x % m) + m) % m` ของ JavaScript ปัดเศษเพิ่มอีกครั้ง → `remEuclid` แบบ `f64::rem_euclid` · hue ที่ตกที่ 360° พอดีใช้ช่วงสุดท้าย
     เหมือน `hsl_to_rgb` (เดิมได้สีเทา) · องศาเป็นเรเดียนใช้ `x * (π/180)` แบบ `to_radians` · `x ** 2` → `x * x` แบบ `powi(2)`
- **ใช้งาน:** แก้สูตรฝั่งไหนต้องแก้อีกฝั่ง ไม่งั้น `cargo test` ไม่ผ่าน · ดูชุดที่ไม่ตรง `PURI_PARITY_ONLY=<ids> PURI_PARITY_DUMP=<ไฟล์>` ·

- **ID:** UUIDv7 แบบข้อความทุกตาราง (เรียงตามเวลาได้ และไม่ชนเมื่อรวมข้อมูลจากฐานเดิม)
