## สำรองและกู้คืน (19 พ.ย. 2569)

เทสต์อัตโนมัติ (`crates/core/tests/backup.rs` + หนึ่งข้อใน `faces_ai.rs`):

| เทสต์ | สิ่งที่พิสูจน์ |
|---|---|
| `t28_backup_then_restore_brings_back_the_backed_up_state_and_keeps_the_replaced_library` | ชุดสำรองมีแค่ `library.sqlite` + `manifest.json` ไม่เหลือไฟล์ชั่วคราว; แก้คลังหลังสำรองแล้วสั่งกู้คืน: คลังที่เปิดอยู่ยังไม่เปลี่ยนจนเปิดใหม่; เปิดใหม่ได้สถานะ ณ ตอนสำรอง; คลังที่ถูกแทนถูกเก็บเป็นชุด `before_restore` และกู้กลับได้; ต้นฉบับไม่ถูกแตะ |
| `restore_refuses_damaged_foreign_and_newer_backups_and_can_be_cancelled` | โฟลเดอร์ที่ไม่ใช่ชุดสำรอง, ไฟล์ที่ถูกแก้หลังสำรอง และชุดจาก schema ใหม่กว่า ถูกปฏิเสธพร้อมเหตุผลและไม่ถูกวางรอ; ไม่สำรองลงโฟลเดอร์รูปที่คลังติดตาม; ยกเลิกการกู้คืนแล้วเปิดใหม่ได้คลังเดิม |
| `automatic_backup_runs_once_a_day_and_keeps_the_latest_sets` | คลังว่างไม่สำรอง; สำรองครั้งแรกแล้วไม่ซ้ำภายในวัน |
| `library_from_v1_upgrades_in_place` (เพิ่ม) | คลัง schema 1 ถูกเก็บเป็นชุด `before_upgrade` ก่อนอัปเกรด และชุดนั้นผ่านการตรวจเพื่อกู้คืน |

ในแอปจริง (หน้าต่าง Tauri, build debug ที่รวมหน้าเว็บในตัว, คลังชั่วคราว): เพิ่มโฟลเดอร์ทดสอบ 15 รูป → ตั้งชื่อหนึ่งคน → สำรอง → ตั้งชื่ออีกคน → สั่งกู้คืน
→ หน้าตั้งค่าแสดงแถบ "รอกู้คืน" → กดปุ่ม "เปิดแอปใหม่ตอนนี้" → แอปเปิดใหม่เอง มีหนึ่งคนตามชุดสำรอง รายการในหน้าตั้งค่ามีชุด "คลังก่อนกู้คืน" (สองคน)
และในเบราว์เซอร์ + dev bridge: กดสำรองและกู้คืนผ่านปุ่มและกล่องยืนยันบนหน้าจอ ดูหน้าตาแล้วเรียบร้อย

ไม่ได้ทำ: สำรองคลังขนาดใหญ่ (ฐาน 400 MB) เพื่อดูเวลา, ดิสก์เต็มหรือถอดไดรฟ์ปลายทางกลางการสำรอง, กู้คืนชุดที่สร้างบนอีกระบบปฏิบัติการ,
ปุ่มเปิดแอปใหม่ใน build ที่เซ็นแล้ว, ทั้งหมดบน Windows นอกจากเทสต์อัตโนมัติที่จะรันบน runner ของ CI

### เชื่อมตำแหน่งโฟลเดอร์ใหม่ (19 พ.ย. 2569)

ในเบราว์เซอร์ + dev bridge แบบ release กับคลังชั่วคราว (โฟลเดอร์ทดสอบ 3 กิจกรรม 15 รูป): ย้ายทั้งโฟลเดอร์แม่ไปที่อื่นจากนอกแอป → หน้ากิจกรรมขึ้น
"โฟลเดอร์ไม่พร้อม" พร้อมปุ่ม "ระบุตำแหน่งใหม่…" → เลือกโฟลเดอร์ของกิจกรรมที่ตำแหน่งใหม่ → กล่องยืนยันแสดงตำแหน่งเดิม/ใหม่, "พบ 6 จาก 6 รูป",
หลักฐานที่ใช้จับคู่ และ "เชื่อมอีก 2 กิจกรรมจากโฟลเดอร์แม่เดียวกันด้วย (9 จาก 9 รูป)" → ยืนยัน → "เชื่อมตำแหน่งใหม่แล้ว 15 รูปใน 3 กิจกรรม" ป้ายเปลี่ยนเป็น "ต้นทางพร้อมใช้"

ไม่ได้ทำ: โฟลเดอร์จริงขนาดใหญ่ (219 กิจกรรม), ย้ายไปไดรฟ์ภายนอกจริง, ไฟล์ที่ถูกเปลี่ยนชื่อหรือย้ายภายในโฟลเดอร์ (ยังจับคู่ไม่ได้ — นับเป็นไม่พบ), ในแอป Tauri เอง

### ย้อนการแจ้ง "ไม่ใช่" (19 พ.ย. 2569)

ในเบราว์เซอร์ + dev bridge แบบ release กับคลังชั่วคราว (ตัววิเคราะห์จริง, 24 รูป, ตั้งชื่อหนึ่งใบ → AI จัดให้ 3 รูป):

## เตรียมแอปให้พร้อมใช้ (`e2e/setup.sh` + `e2e/setup.js` — 20 พ.ย. 2569)

`pnpm tauri dev` บน macOS 26.7 (Apple Silicon) กับคลังว่างในโฟลเดอร์ชั่วคราว ตัววิเคราะห์ใบหน้าเปิดอยู่แต่ยังไม่มีโมเดล
และฐานรุ่น Python จำลอง (`PURI_LEGACY_DB`: 3 คน ชื่อซ้ำหนึ่งคู่ หนึ่งกลุ่ม ใบหน้าตัวอย่าง 4 ใบ) ไม่ออกเครือข่าย

| ขั้น | สิ่งที่ยืนยัน |
|---|---|
| `offered` | เปิดแอปแล้วหน้าต่างเปิดเอง มีปุ่ม "ดาวน์โหลดตัววิเคราะห์ใบหน้า (289 MB)" และปุ่ม "นำเข้า 3 คน"; ปุ่มปิดคือ "ข้ามไปก่อน" |
| `skipped` | กด "ข้ามไปก่อน" แล้ว `get_setup_state.dismissed` เป็นจริง |
| `people-empty` | หน้าบุคคลที่ยังว่างมีปุ่ม "นำรายชื่อจากรุ่นเดิม (3 คน)" ซึ่งเปิดหน้าต่างเดิม |
| `imported` | กดนำเข้าในหน้าต่าง: "นำรายชื่อเข้าแล้ว 3 คน", ไม่เหลือรายชื่อให้นำเข้า, ยังเสนอดาวน์โหลดตัววิเคราะห์ต่อ |
| `people` | "เปิดหน้าบุคคล" ปิดหน้าต่างและแสดง 3 คน; ปุ่มเสนอนำเข้าหายไป |
| `reloaded` | โหลดหน้าใหม่ทั้งที่ยังไม่มีโมเดล: หน้าต่างไม่เปิดเองอีก |

ตรวจบนดิสก์หลังจบ: ฐานรุ่นเดิมเหมือนเดิมทุก byte (SHA-256) และไม่มีไฟล์ `-wal`/`-shm` เกิดข้าง ๆ; คลังมี 3 บุคคล ใบหน้าตัวอย่าง 4 ใบ
และแถว `setup_dismissed` ใน `ui_preferences`; ไม่มีไฟล์โมเดลถูกดาวน์โหลด ภาพหน้าต่างทุกขั้นเปิดดูแล้ว (ธีมมืด)

เทสต์ Rust `legacy_people_import_is_read_only_idempotent_and_only_suggests` เพิ่ม: จำนวนที่รอนำเข้าเป็น 3 ก่อนนำเข้าและ 0 หลังนำเข้า,
`dismiss_setup` เรียกซ้ำได้และ `get_setup_state` จำค่าไว้

**ยังไม่ได้ทดสอบ:** การกดดาวน์โหลดจากในหน้าต่างนี้ (ใช้ปุ่มเดียวกับหน้าอื่น — `FaceModelNotice` — ซึ่งเคยกดผ่านมือกับเครือข่ายจริงแล้ว),
สถานะ "ตัววิเคราะห์พร้อมแล้ว เหลือแต่รายชื่อ" และ "เครื่องนี้วิเคราะห์ไม่ได้ (Intel Mac)", ธีมสว่าง, คลังจริงของผู้ใช้กับฐานจริง 105 คน,
และ Windows (รุ่น Python บน Windows ไม่ทราบตำแหน่งข้อมูล จึงไม่มีข้อเสนอนำรายชื่อ เหลือเฉพาะข้อเสนอดาวน์โหลด)
`e2e/update-published.sh` ถูกแก้ให้กด "ข้ามไปก่อน" ก่อนหา toast ของตัวอัปเดต: การกดผ่าน Accessibility ลองกับ debug build และกับ

### เทสต์อัตโนมัติ (`crates/core/tests/faces_ai.rs`)

ใช้ตัววิเคราะห์จำลองที่มีเฉพาะในโค้ดเทสต์ ("บุคคล" ของรูปทดสอบกำหนดจากค่าสี) และชุดโมเดลจำลองที่ "ดาวน์โหลด" ผ่าน `file://`
ด้วยงานติดตั้งตัวจริง — เทสต์นี้พิสูจน์กติกาข้อมูลรอบ AI ไม่ใช่ความแม่นยำของโมเดล

|---|---|
| `model_is_optional_then_one_click_install_analyses_existing_photos` | ไม่มีโมเดล: เพิ่มและดูรูปได้ครบ, "ยังไม่ได้วิเคราะห์" ≠ "ไม่พบใบหน้า" (T09); ติดตั้งด้วยคำสั่งเดียว (กดซ้ำได้งานเดิม) → เก็บเฉพาะไฟล์ที่ใช้ → รูปเดิมถูกวิเคราะห์ต่อเอง; สแกนซ้ำ/เปิดใหม่ไม่เกิดใบหน้าซ้ำ; รูปใหม่ถูกวิเคราะห์ในงานเดียวกับการเตรียมข้อมูล |
| `corrupt_download_is_refused_and_can_be_retried` | ไฟล์ที่ checksum ไม่ตรงไม่ถูกใช้ งานล้มเหลวพร้อมเหตุผล; ดาวน์โหลดใหม่แล้วใช้ได้ |

| `legacy_people_import_is_read_only_idempotent_and_only_suggests` | ฐานเดิมไม่ถูกแก้แม้ byte เดียว; retry และรันซ้ำไม่สร้างคนซ้ำ (T29 บางส่วน); ชื่อซ้ำเป็นคนละคน; เวกเตอร์เดิมไม่ถูกใช้; ภาพตัวแทนจากใบหน้าตัวอย่าง; ข้อเสนอจากข้อมูลเดิมไม่นับเป็นยืนยันแล้วจนกว่าผู้ใช้ยืนยัน |

แล้วขับผ่านหน้าต่างจริงของแอป ไม่มีขั้นไหนเรียกตัวอัปเดตตรง ๆ ยกเว้นการอ่านสถานะ

| ขั้น | สิ่งที่พิสูจน์ |
|---|---|
| `opened` | แอปรุ่น 2.0.0-alpha.3 เปิดจากตำแหน่งที่ติดตั้ง ตัวอัปเดตเปิดใช้ |
| `rejected` | แอป**ตรวจเองหลังเปิด** พบรุ่น 99.0.0 ดาวน์โหลดไฟล์ที่ถูกเติมหนึ่ง byte ภายใต้ลายเซ็นของไฟล์จริง → ไม่ผ่านลายเซ็น: หน้าตั้งค่าบอกเหตุ ไม่มีปุ่มติดตั้ง และ `.app` บนดิสก์ยังเป็นรุ่นเดิม |

| `confirm` | ปุ่มในเมนูซ้ายเปิดกล่องยืนยัน ซึ่งแสดงข้อความ "มีอะไรใหม่" จาก manifest |

ตัวรันตรวจบนดิสก์หลังจบ: `Info.plist` เป็นรุ่นใหม่, `.app` ที่ติดตั้งตรงกับผล build ทุกไฟล์ (`diff -r`), process ทำงานจากตำแหน่งเดิม, คลังยังอยู่,
ไม่เหลือโฟลเดอร์ชั่วคราวของตัวอัปเดตข้างแอป

รันสองแบบ ผ่านทั้งคู่: (1) กุญแจชั่วคราวที่เทสต์สร้างเอง (2) `REAL_KEY=~/.config/puriphotosearch/updater.key` กับกุญแจสาธารณะใน `tauri.conf.json`
ตามที่เป็น — แบบที่สองพิสูจน์ว่ากุญแจที่เก็บไว้เป็นคู่ของกุญแจสาธารณะที่จะฝังไปกับแอป และว่า `requireSignedVersion` รับลายเซ็นที่ `tauri build` สร้าง

หน้าจอ (หมวดอัปเดตในตั้งค่าทุกสถานะ, ปุ่มในเมนูซ้ายแบบเต็มและแบบยุบ, กล่องยืนยัน, ธีมมืด) เปิดดูด้วยตาในเบราว์เซอร์ผ่าน dev server
โดยตั้งสถานะจาก console — ในเบราว์เซอร์และ debug build ที่ไม่ได้ตั้งปลายทาง หมวดนี้แสดงว่า "เป็นรุ่นสำหรับพัฒนา ไม่ตรวจหารุ่นใหม่"

`e2e/run.sh` (เส้นทางหลัก 14 ขั้น) รันซ้ำหลังเพิ่มตัวอัปเดต: ผ่าน — debug build ที่ไม่ได้ตั้ง `PURI_UPDATE_ENDPOINT` ไม่ออกเครือข่าย

**ยังไม่ได้ทดสอบในชุดนี้:** (release build ที่เซ็น + notarize เป็นฝ่ายถามและอัปเดตตัวเองจาก GitHub จริง — ทดสอบแล้วภายหลัง ดู "รุ่น 2.0.0-alpha.5 ที่เผยแพร่")
แอปใน `/Applications` ที่ต้องขอสิทธิ์ผู้ดูแลเครื่อง, แอปที่เปิดจาก `.dmg` โดยตรง (มีข้อความเฉพาะ แต่ไม่ได้ลอง), เครือข่ายหลุดกลางการดาวน์โหลด,
การตรวจซ้ำทุก 6 ชั่วโมง, สวิตช์ปิดการตรวจอัตโนมัติ (เปิดดูแล้ว ไม่อยู่ในเทสต์), Intel Mac, เครื่อง Windows จริง

### workflow `Release` รอบซ้อมของ PR #17 ก่อนมี secret ของกุญแจ

ทุก job ผ่าน: `macos` (เซ็น + notarize + staple ตามเดิม, `spctl` รับ DMG เป็น `Notarized Developer ID`), `windows`, `update-windows`, `manifest`; `publish` ถูกข้ามเพราะไม่ใช่ tag
รอบนี้**ไม่มี** `TAURI_SIGNING_PRIVATE_KEY` workflow จึงเดินทาง "ไม่มีกุญแจ": เตือนว่า build นี้ใช้เป็นอัปเดตในแอปไม่ได้ สร้างตัวติดตั้งตามปกติ และไม่เขียน manifest

### workflow `Release` รอบซ้อมที่มีกุญแจ (`workflow_dispatch` บน branch หลังเจ้าของตั้ง secret `TAURI_SIGNING_PRIVATE_KEY` — 19 พ.ย. 2569)

ทุก job ผ่าน (`publish` ถูกข้ามเพราะไม่ใช่ tag) ดาวน์โหลด artifact มาตรวจในเครื่อง:

| ตรวจ | ผล |
|---|---|
| ไฟล์อัปเดต | `PuriPhotoSearch-mac.app.tar.gz` 20.2 MiB + `.sig`, `PuriPhotoSearch-windows-setup.exe` 9.9 MiB + `.sig` (ตัวติดตั้งตัวเดียวกับที่ให้ดาวน์โหลด) |
| ไฟล์อัปเดตของ macOS คือแอปที่ notarize แล้ว | บน runner: แตก `.tar.gz` แล้ว `codesign --verify --deep --strict` ผ่าน, `diff -r` กับ `.app` ที่ build ไม่ต่าง, `stapler validate` ผ่าน, `spctl` รับเป็น `Notarized Developer ID` |
| ลายเซ็นตรงกับกุญแจสาธารณะใน `tauri.conf.json` | ตรวจในเครื่องด้วย `openssl` (Ed25519 บน BLAKE2b ของไฟล์ ตามรูปแบบ minisign): ลายเซ็นของไฟล์ถูกทั้งสองระบบ, ลายเซ็นของ trusted comment ถูก, ไฟล์ที่เติมหนึ่ง byte ไม่ผ่าน — secret บน GitHub จึงเป็นกุญแจคู่เดียวกับที่ฝังในแอป |
| เลขรุ่นที่ผูกกับลายเซ็น | trusted comment ของทั้งสองไฟล์มี `version:2.0.0-alpha.3` (สิ่งที่ `requireSignedVersion` ตรวจ) |
| `latest.json` จาก job `manifest` | `version` ตรงกับ `tauri.conf.json`, มี `darwin-aarch64` + `darwin-x86_64` (ไฟล์เดียวกัน) + `windows-x86_64`, URL ชี้ `releases/download/v<รุ่น>/<ชื่อไฟล์คงที่>`, `notes` ว่างพร้อมคำเตือนว่าไม่มี `docs/release-notes/<รุ่น>.md` |

job `publish` รันเฉพาะ tag จริง จึงไม่อยู่ในรอบซ้อมนี้ — ดูหัวข้อถัดไป
สคริปต์ `scripts/update-manifest.sh` ตัวเดียวกันนี้ถูกใช้และผ่านใน `e2e/update.sh` แล้วทั้งสองระบบ

### รุ่น 2.0.0-alpha.5 ที่เผยแพร่ (19 พ.ย. 2569) — แอปที่เผยแพร่อัปเดตตัวเองจริงครั้งแรก

push tag `v2.0.0-alpha.5` → workflow `Release` ผ่านทุก job; ไฟล์ที่ดาวน์โหลดกลับมาตรงกับ `SHA256SUMS.txt` ทั้งสามไฟล์, DMG ผ่าน `stapler validate` และ `spctl`,
`latest.json` บน branch `updates` ตรงทุก byte กับที่แนบใน release

`e2e/update-published.sh` (ใหม่) บน macOS 26.7 / Apple M4 — **ทั้งสองฝั่งเป็นไฟล์ที่เผยแพร่จริง ไม่มี build ของเราเองเกี่ยวข้อง**:

| ขั้น | ผล |
|---|---|
| ติดตั้ง | แตก `PuriPhotoSearch-mac.app.tar.gz` ของ release `v2.0.0-alpha.4` ลงโฟลเดอร์ชั่วคราว: รุ่น 2.0.0-alpha.4, `spctl` รับเป็น `Notarized Developer ID`, เปิด hardened runtime |
| พบรุ่นใหม่เอง | เปิดด้วย `HOME` ชั่วคราว ไม่มีตัวแปรของเทสต์ใด ๆ: 9 วินาทีหลังเปิด แอปขึ้น toast "รุ่น 2.0.0-alpha.5 พร้อมติดตั้งแล้ว" — คือถาม `latest.json`, ดาวน์โหลด 20.2 MiB จาก release และผ่านลายเซ็นแล้ว |
| กล่องยืนยัน | กดปุ่ม "อัปเดต" ของ toast ผ่าน Accessibility → กล่อง "อัปเดตเป็นรุ่น 2.0.0-alpha.5" บอกรุ่นที่ใช้อยู่ และแสดง "มีอะไรใหม่" จาก `docs/release-notes/2.0.0-alpha.5.md` ครบสองบรรทัด |
| ติดตั้งและเปิดใหม่ | กด "อัปเดตและเปิดใหม่" → `.app` ในที่เดิมเป็น 2.0.0-alpha.5 (`codesign --verify --deep --strict` ผ่าน, `spctl` รับ), process ใหม่เปิดขึ้นมาเองและแสดงหน้าเริ่มต้น, ไม่เหลือโฟลเดอร์ชั่วคราวข้างแอป, คลังจริงของผู้ใช้ไม่เปลี่ยน |

รันสามรอบ (สองรอบจากสคริปต์ต้นร่าง หนึ่งรอบจากไฟล์ใน repo) ผลเดียวกัน รอบแรกสุดล้มที่ตัวสคริปต์เอง ไม่ใช่ที่แอป: Accessibility มองไม่เห็นหน้าต่างที่อยู่บน Space อื่น
จึงเพิ่มการดึงหน้าต่างขึ้นมาข้างหน้าก่อนอ่านหรือกด และ WebKit สร้างต้นไม้ accessibility หลังถูกถามครั้งแรก จึงถามซ้ำ

**ยังไม่ได้พิสูจน์:** แอปใน `/Applications` ของผู้ใช้จริง (เทสต์ใช้โฟลเดอร์ชั่วคราวที่เขียนได้ จึงไม่ผ่านทางขอสิทธิ์ผู้ดูแลเครื่อง), การอัปเดตข้ามรุ่นที่คลังต้องยกระดับ schema โดยมีข้อมูลจริงอยู่
(คลังในเทสต์ว่าง), Intel Mac, การปฏิเสธ tag ที่ไม่ตรงเลขรุ่น (ไม่เคยเกิด) และ **Windows กับไฟล์ที่เผยแพร่จริง** — job `update-windows` ทดสอบ debug build ของ commit เดียวกันบน runner (ผ่านทั้งสองรุ่น)
ยังไม่เคยมีแอป Windows ที่เผยแพร่อัปเดตตัวเอง

### Windows (job `update-windows` ของ workflow `Release`, runner `windows-latest` — รอบซ้อมของ PR #17)

สคริปต์เดียวกัน แต่ "ติดตั้ง" ด้วยตัวติดตั้ง NSIS จริงแบบเงียบ (`/S`) ลง `%LOCALAPPDATA%\Puri Photo Search` แล้วเปิดแอปจากที่นั่น:
ผ่านขั้น `opened` → `rejected` (ข้อความไม่ผ่านลายเซ็นขึ้นในหน้าตั้งค่า) → `ready` (ดาวน์โหลดตัวติดตั้งรุ่นใหม่ 11.4 MB) → `confirm` → กด "อัปเดตและเปิดใหม่"
→ แอปปิด, ตัวติดตั้ง 99.0.0 รันแบบ passive, เลขรุ่นที่ตัวติดตั้งบันทึกใน registry (`DisplayVersion`) เปลี่ยนจาก 2.0.0-alpha.3 เป็น 99.0.0, และมี process ของแอปทำงานอยู่หลังจากนั้น

**ที่ยืนยันไม่ได้บน Windows:** ตัวติดตั้งเปิดแอปใหม่ผ่าน shell ซึ่งไม่ส่งตัวแปรของเทสต์ต่อให้ แอปรอบสองจึงไม่ได้รายงานเลขรุ่นของตัวเองกลับมา —
หลักฐานว่าเป็นรุ่นใหม่คือเลขรุ่นใน registry กับ process ที่ทำงานอยู่ ไม่ใช่คำตอบจากในแอป (บน macOS ยืนยันจากในแอป) และไม่มีใครเห็นหน้าต่างของตัวติดตั้งด้วยตา
